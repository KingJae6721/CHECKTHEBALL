# CheckTheBall — Offline / Online Test

김영재의 1인칭 브라우저 농구 프로토타입. 기존 오프라인 연습과 두 사람이 쓰는 서버 권위 온라인 자유 연습을 제공합니다. 온라인은 정식 1v1 경기가 아닙니다.

## 실행

Node.js 24와 npm을 사용합니다. npm 패키지 이름은 `check-the-ball`이며, 의존성은 루트 `package.json`과 `package-lock.json`에서 관리합니다. Windows PowerShell에서도 아래 명령을 사용합니다. PowerShell 실행 정책으로 `npm.ps1` 실행이 차단되면 `npm` 대신 `npm.cmd`를 사용하세요.

```bash
npm ci
npm run dev:next
# http://localhost:3000 또는 /play
npm test
npm run typecheck
npm run build
```

Next.js App Router / TypeScript / Babylon.js. 빌드 결과는 `apps/web/out` 및 배포용 `out`.

## 조작

플레이 버튼으로 마우스를 잠급니다. 마우스로 시선과 좌우 조준, WASD 이동, Shift 달리기, Space 점프, 좌클 누르기/놓기 슛 충전/발사, R 초기화, Esc 일시정지.

초록 구간에서 릴리스하면 타이밍 오차가 작습니다. 좌우 조준은 수동이고 높이는 보조됩니다. 아크 안 1점, 밖 2점. 슛 후에는 발 주변의 공을 줍거나 몸통 앞 영역에서 바운드 중인 공을 잡습니다. 공 소유 중 우클을 눌러 패스 세기를 충전하고 놓으면 시선 방향으로 패스하며, 더미가 받으면 잠시 뒤 반환 패스를 합니다. 공 미소유 시 좌클 스틸 / 우클 블록을 사용할 수 있습니다. Esc 메뉴에서 패스·스틸·블록·공격 자세 시나리오를 선택합니다.

## 구조

- `apps/game-server`: 별도 Node.js Colyseus BasketballRoom. 서버에서 하나의 월드/공을 판정합니다.
- `packages/protocol`: 입력 의도·검증 범위·네트워크 주기 타입과 설정.
- `apps/web`: Next.js App Router + Babylon.js 프론트엔드
- `packages/game-core`: 렌더러와 독립적인 게임 상태·이동·점프·슛·득점 규칙. DOM, Babylon.js, Next.js 및 네트워크에 의존하지 않습니다.
- `packages/game-core/src/simulation.ts`: DOM/렌더러와 분리한 게임 상태, 고정 틱 이동, 점프, 충전, 탄도, 득점 규칙
- `packages/game-core/src/motion.ts`: controlled ball 드리블·Gather·캐치·릴리스 및 논리 hand socket/자세
- `apps/web/game/createCharacter.ts`: 공용 TransformNode 관절 표시 어댑터 (1인칭 팔/다리와 더미 전신)
- `apps/web/game/createGame.ts`: Babylon Scene, 카메라, 입력 수명 주기, LocalSimulation 루프, HUD 스냅샷
- `apps/web/app/Game.tsx`: 페이지와 HUD

현재 LocalSimulation은 `apps/web/game/createGame.ts` 안의 로컬 실행 루프를 뜻하며, 별도 클래스나 서버가 아닙니다. 이 루프가 `game-core` 함수를 호출해 이동·점프·슛·득점을 로컬에서 판정합니다. 프론트엔드는 브라우저 입력, 시뮬레이션 실행, 렌더링과 HUD를 연결하고, 규칙 자체는 `game-core`에서 유지합니다.

현재 각 디렉터리에 별도 `package.json`을 두지 않고 루트 npm 스크립트와 소스 import로 연결합니다. `pnpm-workspace.yaml`의 디렉터리 선언은 유지하지만 현재 설치·실행·lockfile 관리는 npm 기준입니다. 최상위 작업 폴더 이름은 브랜드 이름과 무관하며 변경할 필요가 없습니다.

게임 상태를 원본으로 사용하며 Mesh는 상태를 표시합니다. 60Hz는 시뮬레이션 설정값이고 성능 측정 결과가 아닙니다. 매 프레임 최대 6 substep, 100ms delta clamp를 사용하며 포커스 상실과 마우스 잠금 해제 시 입력/충전을 초기화합니다.

## 검증

기존 규칙 테스트 9개: 대각선 정규화, 경계, 점프/착지, 중복 슛 방지, 하강 득점, 완전 타이밍 슛의 중복 득점 방지/공 반환, 릴리스 시 점수 고정, 충전 취소, 동일 입력 재현.

## 공 충돌과 반사 (Sprint 1 후속)

게임 상태가 물리 판정의 원본입니다. packages/game-core/src/court.ts의 COURT를 시뮬레이션과 Babylon 렌더러가 공유합니다. physics.ts는 렌더러 독립 수치 충돌 처리, simulation.ts는 슛 결과·점수·반환 규칙을 담당합니다. Mesh 충돌이나 외부 물리 엔진은 사용하지 않습니다. 오프라인 판정은 LocalSimulation, 온라인 판정은 별도 Colyseus 서버에서 수행합니다.

공통 형상 (단위 m): 공 반지름 0.12, 바닥 높이 0.012, 백보드 중심 (0, 3.55, 6.1)과 크기 (1.8, 1.05, 0.07), 림 중심 (0, 3.05, 5.7), 중심선 반지름 0.24, 튜브 반지름 0.0175입니다. 백보드는 유한 AABB의 최근접점으로 판정하며 중심이 내부에 있으면 가장 가까운 면으로 밀어냅니다. 림은 48개 선분 캡슐의 합입니다. 득점 여유 반경은 rimRadius * cos(PI / rimSegments) - rimTubeRadius - ballRadius로 선분 근사의 안쪽 반경까지 보수적으로 반영합니다.

설치된 Babylon.js 8.56.2의 node_modules/@babylonjs/core/Meshes/Builders/torusBuilder.js에서 CreateTorusVertexData를 확인했습니다. 중심선을 diameter / 2만큼 이동하고 단면을 thickness / 2로 만듭니다. 따라서 렌더링은 diameter = 2 * rimRadius, thickness = 2 * rimTubeRadius입니다. 생성 정점의 안쪽/바깥 반경과 튜브 높이도 공통 설정과 1µm 허용오차 내 일치함을 별도 수치 검증했습니다. 캡슐은 다각형 Torus 표면의 수치 근사로, 삼각형 표면과 완전히 동일한 충돌체는 아닙니다. 바닥의 페인트·라인은 시각 장식이며 별도 충돌체가 아닙니다.

반사는 v' = v - (1 + restitution) * dot(v, normal) * normal이며 접근 속도일 때만 적용하고 반발계수는 0~1로 제한합니다. 림은 반복마다 가장 깊은 접촉 하나만 처리하고 전체 접촉 반복은 최대 4회입니다. 바닥 정지 시 중력 적분을 건너뛰어 미세 진동을 막습니다.

튜닝 위치는 court.ts의 PHYSICS입니다. 아래 값은 초기 게임 감각 튜닝이며 실제 재질 측정값이 아닙니다.

| 물체 | 반발계수 | 마찰/감쇠 |
| --- | --- | --- |
| 바닥 | 0.68 | 접지 시간에 대해 수평 속도에 exp(-1.8 * dt) 적용 |
| 백보드 | 0.72 | 접근 충격의 접선 속도 8% 감소 |
| 림 | 0.62 | 접근 충격의 접선 속도 12% 감소 |

바닥 반사 후 수직 속도 0.22 m/s 미만이면 수직 정지, 접지 수평 속도 0.05 m/s 미만이면 수평 정지합니다. 보드/림 마찰은 충격당 감쇠이고 바닥 감쇠는 시간 기준입니다. 회전·스핀·각운동량·변형·림/그물 움직임은 모델링하지 않습니다.

관통 방지는 이동량에 따른 bounded substep으로 처리합니다. 이동량을 공 반지름·보드 두께·림 튜브 지름의 최솟값 절반(현재 0.0175m) 이하로 나눕니다. 물리 틱은 최대 1/30초, 최대 192 substep, 입력 공 속도는 0~80 m/s 지원이며 초과 속도는 80 m/s로 제한합니다. 기본 중력 9.81 m/s²에서 최대 속도와 최대 dt 조합도 예산 안에 들어갑니다. 범위를 벗어난 dt는 오류로 처리하며 일반 게임 루프는 기존 1/60초 고정 틱을 사용합니다. 형상·중력·속도 설정을 변경하면 이 예산도 재검증해야 합니다. 연속 시간의 정밀 충돌 시각을 계산하는 swept solver는 아닙니다.

충돌로 보정한 각 substep 경로가 림 안을 하강 통과할 때만 득점합니다. 첫 바닥 접촉은 실패를 확정하지만 반사는 계속되며 결과 확정 플래그가 중복 득점을 막습니다. 릴리스 위치의 1/2점 규칙은 유지합니다. 결과 확정 후 공은 회수 가능한 자유 상태가 됩니다. 이전의 1.2~2.5초 자동 반환은 제거했으며 아래 회수·안전 복구 정책을 적용합니다. 기존 완전 타이밍 슛이 물리 림을 넘도록 보조 탄도의 비행시간 기본항을 0.75초에서 0.9초로 높인 설정은 유지합니다.

개발 서버(npm run dev:next)에서 **F3**로 녹색 백보드·림, 파란 발 주변 회수 영역, 노란 몸통 앞 캐치 영역과 획득 디버그 패널을 켜고 끕니다. 초기에는 숨겨져 있고 프로덕션에서는 만들지 않습니다. 디버그 Mesh도 판정에 사용하지 않습니다.

물리 회귀 테스트 18개를 추가했습니다. 바닥 반사·감쇠·정지·관통 보정, 시간 간격에 따른 마찰 일치, 보드 정면/가장자리/외부/내부, 림 반사/중앙 통과, 이탈 속도, 최대 속도 관통 방지, 무중력 접촉의 비에너지 증가, 득점 경로·중복 방지, 실패 후 바운드, 반환 후 재슛과 제한시간을 검증합니다. 충돌 단계까지 기존 9개와 합계 27개이며, 이번 패스 단계 테스트는 아래에 추가했습니다. 초기 충돌 단계에서는 실제 브라우저 검증을 하지 못했지만, 후속 패스 작업에서 아래 headless Chrome 검증을 추가했습니다. F3 개발용 오버레이는 이번 프로덕션 브라우저 검증 대상에서 제외했습니다.

## 자유 공 회수와 패스 더미

공 흐름은 자유 공 회수 → 우클 누르기/놓기 패스 → 더미 캐치 → 0.7초 보유 → 반환 패스 → 플레이어 캐치입니다. 더미를 빗겨 던지거나 반환 공을 이동해서 놓치면 자유 공을 다시 회수합니다. HUD는 PLAYER/더미/자유 공과 비행 상태, 패스 대상 조준, 우클 패스 또는 회수 안내를 표시합니다. 우클 context menu는 캔버스에서 차단하고 누르는 동안 충전하며 놓을 때 한 번만 발사합니다.

소유권은 game-core State.owner의 player / dummy / none 하나로 표현하며 State.flightKind는 shot / pass / null입니다. Phase는 HELD(소유), CHARGING(슛 충전), PASS_CHARGING(패스 충전), IN_FLIGHT(슛/패스), RESOLVING(자유 공)으로 사용합니다. 소유권을 잃으면 충전을 취소하고 캐치 시 속도를 0으로 초기화합니다. Babylon은 이 상태만 표시하며 소유권·캐치를 판정하지 않습니다. 패스는 슛 시도·명중·점수에 영향을 주지 않고 골대를 통과해도 득점하지 않습니다.

튜닝 위치는 packages/game-core/src/court.ts의 **DUMMY**, **PRACTICE**, **ACQUISITION**, **PASS**, **PLAYER**입니다. 초기 튜닝값이며 실제 측정값은 아닙니다.

| 항목 | 현재 값 |
| --- | --- |
| 더미 위치 / 키 | (3, 바닥 높이, 1.5)m / 1.8m |
| 더미 캐치 위치 | 몸통 앞 0.38m, 바닥 위 1.28m |
| 바닥 줍기 | 발 주변 박스, 바닥 위 0~0.5m, 속도 ≤14m/s (세부 영역은 아래 ACQUISITION 참고) |
| 공중 캐치 | 몸통 앞 박스, 발 위 0.5~1.75m, 속도 ≤18m/s |
| 자기 공 재획득 금지 | 발사 후 0.45초 |
| 플레이어 패스 속도 | 시선 벡터 × 7~22m/s, 최대 충전 1.2초 |
| 더미 반환 패스 | 목표점 계산, 수평 8m/s |
| 플레이어 자동 조준/높이 보조 | 없음. 더미 방향 힌트만 반각 0.20rad, 최대 18m |
| 패스 캐치 | 중심 거리 ≤0.42m, 높이 오차 ≤0.36m, 속도 ≤28m/s |
| 더미 보유 | 0.7초 |
| 패스 비행 종료 | 첫 바닥 접촉 또는 4초 경과 시 자유 공 |
| 슛 비행 제한 | 기존 8초; 이후 자유 공 |
| 안전 복구 | x/z 절댓값 12m 초과 또는 자유 상태 30초 방치 시 플레이어에게 회수 |

바닥 줍기와 공중 획득은 소유자가 없는 자유 공 및 아래 자격을 만족한 자신의 슛을 처리합니다. 다른 캐릭터의 소유 공과 진행 중인 패스는 이 경로로 획득하지 않으며 패스는 기존 캐치 규칙을 사용합니다. 공을 회수하면 기존 플레이어 보유 위치에 표시합니다. 일반적인 실패에는 짧은 시간 반환하지 않아 직접 회수할 수 있습니다. 코트 주변 여유 공간을 포함한 안전 경계가 12m이므로 사이드라인 직후에도 공을 관찰·회수할 여유가 있습니다.

플레이어 패스는 발사 순간의 yaw/pitch 방향 벡터에 충전 세기의 속도를 곱합니다. 더미 방향 표시는 힌트이며 자동 조준이나 높이 보조를 적용하지 않습니다. 중력으로 포물선이 생기므로 거리와 세기에 맞춰 조준 높이도 직접 조절합니다. 모든 발사 후에는 기존 중력·바닥/백보드/림 충돌을 사용합니다. 더미 반환만 별도의 목표점 계산을 유지합니다.

패스 캐치는 매 물리 substep의 이동 구간과 수신자의 캐치 영역 최근접점으로 검증합니다. 충돌 보정을 먼저 적용하고, 충돌한 구간은 캐치 경로에서 제외합니다. 발사 시 플레이어부터 앞쪽 릴리스 위치까지, 캐치 시 캐치 지점부터 수신자까지 공 반지름을 고려한 백보드/림 경로 검사도 수행해, 캐치 영역이 골대 뒤까지 겹쳐도 공을 끌어오지 않습니다. 더미는 플레이어가 던진 비행 중 패스만 캐치하며 자유 공이나 멀리 있는 공을 자동 획득하지 않습니다.

더미는 기본 구·박스·실린더를 실제 관절 pivot의 TransformNode 계층으로 연결해 머리/몸통/팔/손/다리를 구분합니다. 상세 치수, 바닥 표시와 이름표 크기도 DUMMY에서 관리합니다. 제자리에서 플레이어를 바라보며 캐치·드리블·Gather·반환 동작을 합니다. 이동 AI나 스킨/스켈레탈 애니메이션은 없습니다. 플레이어는 더미와 겹치지 않도록 최소 거리를 유지합니다. 더미는 반환 발사 순간의 플레이어 위치를 향한 초기 속도를 한 번 계산하며 발사 후 추적하지 않습니다. 몸통에 빗맞은 공의 인체 충돌과 장식 울타리 충돌은 구현하지 않았습니다.

R/세션 초기화는 resetState로 플레이어·소유권·공·더미 보유시간·발사 이력·안전 복구시간을 함께 초기화합니다. 반환 예약은 setTimeout이 아닌 시뮬레이션 상태의 dummyHold로 관리하므로 초기화/일시정지 후 오래된 반환 콜백이 실행되지 않습니다.

패스·회수 테스트 21개를 추가했습니다. 기존 27개 중 수동으로 비행을 만든 테스트는 소유권/비행 원인을 명시했고, 짧은 반환을 기대하던 테스트는 자유 공 회수·안전 복구 정책을 검증하도록 수정했습니다. 합계 48개로 줍기 임계값, 소유 공 탈취 방지, 자기 공 재획득 제한, 패스 거부, 왕복/빗나감, 이동 구간 캐치, 골대 너머 캐치 차단, 통계 분리, 초기화와 더미 겹침 방지를 검증합니다. 2026-11-04 Windows / Node.js 24.11.1에서 npm test(48/48), npm run typecheck, npm run build가 통과했습니다. / 및 /play 정적 페이지와 배포용 out을 생성했습니다.

추가로 로컬 정적 배포 파일을 임시 프로필의 headless Chrome + SwiftShader(WebGL 소프트웨어 렌더링)에서 실행했습니다. WebGL 초기화와 Pointer Lock, 더미의 머리/몸통/팔/다리·바닥 표시·이름표·조준 HUD를 확인했습니다. 실제 캔버스 우클 입력으로 플레이어 패스 → 더미 보유 → 반환 패스 → 플레이어 캐치가 표시됐고, 우클 메뉴 차단·버튼 보유 중 재발동 방지·통계 0/0 및 점수 0 유지도 확인했습니다. R 초기화 후 골대 근처로 이동해 슛하고, 자유 공이 떨어진 쪽으로 접근하자 '공 회수 · 우클로 패스하세요'와 플레이어 소유 상태로 전환됐습니다. 이 브라우저 실행에서 런타임 예외는 없었습니다. 일반 창에서 사람의 수동 조작, 실제 GPU 렌더링·성능과 다른 브라우저는 미검증입니다.

## 바운드 중 공 획득 개선

이전에는 슛 판정이 끝난 자유 공만 바닥 위 0.55m 이하·전체 속도 2m/s 이하에서 획득했습니다. 바운드 횟수 제한은 없었지만 이 높이·속도 조합 때문에 여러 번 튀어야 잡히는 문제가 있었습니다. 현재는 바닥 줍기와 공중 캐치를 분리하며 일반적인 바운드를 막던 2m/s 제한을 제거했습니다.

렌더러 독립 판정은 packages/game-core/src/acquisition.ts에 있고 영역·최대 속도는 court.ts의 ACQUISITION에서 관리합니다. 좌표는 플레이어의 수평 yaw 기준이며 pitch로 영역을 머리 위로 올리지 않습니다. 아래 범위는 공 중심 기준의 초기 튜닝값으로 실제 측정값이 아닙니다.

| 영역 | 좌우 | 앞뒤 | 높이 | 최대 속도 |
| --- | --- | --- | --- | --- |
| 발 주변 GROUND_PICKUP | ±0.8m | 뒤 0.25m ~ 앞 0.85m | 월드 바닥 위 0~0.5m | 14m/s |
| 몸통 앞 AIR_CATCH | ±0.6m | 앞 0.08~1.25m | 플레이어 발 위 0.5~1.75m | 18m/s |

바닥 줍기는 플레이어 발이 지면에서 0.12m 이내일 때 활성화합니다. 공중 캐치는 몸통 앞에 한정하여 등 뒤·머리 위·측면의 공을 거리만으로 가져오지 않습니다. 자유 공은 상승 중이든 하강 중이든 영역에 들어오면 획득할 수 있습니다. 가까이 있다는 이유로 위의 속도 상한을 넘는 공까지 잡지는 않습니다.

자기 슛은 다음 자격을 검사합니다. 기존 발사 직후 0.45초 재획득 방지는 유지합니다. 이후 림/백보드/바닥 접촉 이력(shotTouched)이 있거나 득점·실패가 확정됐으면 회수할 수 있습니다. 접촉하지 않은 에어볼은 공 전체가 획득 영역을 벗어난 이력(shotExited)이 있고 현재 하강 중이어야 합니다. 완전 이탈은 영역을 공 반지름만큼 확장한 범위에서도 벗어났는지로 보수적으로 판정합니다. 아직 결과가 나지 않은 자기 슛을 잡으면 실패로 확정해 뒤늦은 득점을 막습니다. 상대 슛의 블록/리바운드 규칙은 추가하지 않았고 패스 캐치 영역·충돌 순서는 유지합니다. 이후 수동 충전 패스 도입에서 패스 캐치 속도 상한만 28m/s로 조정했습니다.

매 물리 substep에서 이전~현재 공 중심 구간과 회전된 박스의 slab 교차로 빠른 공의 획득을 검사합니다. 충돌을 먼저 처리하며, 관통 보정이 있던 구간은 보정 후 위치만 검사해 보정 이동을 캐치 경로로 오인하지 않습니다. 캐치 지점~손 앞 기준점~몸통과 공의 이동 경로를 공 반지름을 고려한 백보드/림 차폐 검사로 확인하므로 골대 너머에서 끌어오지 않습니다. 기존 장식 울타리는 충돌체가 아닙니다.

일반 바운드·굴러가는 공에 짧은 반환 타이머를 추가하지 않았습니다. x/z 절댓값 12m 초과와 자유 공 상태 30초 방치의 안전 복구만 유지합니다. 시간은 포커스 상실/일시정지를 제외한 시뮬레이션 시간입니다. 획득 이벤트는 순간이동 전에 이유·위치·비행 시간·자유 시간을 기록합니다.

F3 개발 패널의 최근 사유:

- GROUND_PICKUP: 발 주변 영역에서 정상 획득
- AIR_CATCH: 몸통 앞 영역에서 정상 획득
- OUT_OF_BOUNDS: x/z 절댓값 12m를 넘어서 안전 복구
- RECOVERY_TIMEOUT: 자유 상태가 30초 지속되어 안전 복구

현재 차단 사유도 표시합니다. OWNED_BY_PLAYER / OWNED_BY_DUMMY는 이미 소유 중, PASS_IN_FLIGHT는 기존 패스 캐치 경로 사용, RELEASE_LOCK은 발사 직후 재획득 금지, AIRBALL_NOT_LEFT는 에어볼의 완전 이탈 이력 없음, AIRBALL_RISING은 에어볼 상승 중, UNSUPPORTED_SHOT은 이번에 다루지 않는 상대 슛, OUTSIDE_VOLUMES는 획득 영역 밖, TOO_FAST는 영역별 속도 초과, OBSTRUCTED는 백보드/림 차폐입니다. 정상 획득 가능한 경우는 NONE입니다. 최근 이벤트는 다음 획득/복구까지 유지하고 R 초기화 시 이력과 함께 지웁니다. 기본/프로덕션 화면에는 개발 표시를 노출하지 않습니다.

실제 원인 재현: 초기 위치에서 완전 타이밍 슛 후 가만히 있으면 약 2.33초, z=12.02m에서 OUT_OF_BOUNDS가 기록됐습니다. 이는 바운드 횟수나 짧은 반환 타이머가 아니라 경계 이탈입니다. 개별 플레이에서는 F3의 최근 사유와 기록 위치/시간으로 정상 획득인지 안전 복구인지 구분할 수 있습니다.

획득 회귀 테스트 23개를 추가해 기존 48개와 총 71개가 통과했습니다. 바닥 줍기, 바운드 상승/하강 캐치, 발사 직후 잠금, 완전 이탈 후 하강 에어볼, 림/백보드/첫 바닥 접촉, 머리 위·등 뒤 제외, 속도 상한과 이동 구간, 소유 공 보호, 패스 캐치 유지, 차폐 및 두 복구 사유를 검증합니다. npm run typecheck와 npm run build도 통과했습니다.

실제 브라우저 확인: 기존 개발 서버를 임시 프로필의 headless Chrome + SwiftShader로 열어 Pointer Lock, F3 영역/차단 사유 패널과 패스 왕복을 확인했습니다. 골대 앞 슛의 접촉 후 약 0.60초에 AIR_CATCH(높이 약 1.7m), 바닥 접근 시 GROUND_PICKUP이 기록됐습니다. 별도 비조준 패스는 약 1.65초, z=12.1m에서 OUT_OF_BOUNDS로 복구되는 것이 패널에 표시됐습니다. 런타임 예외는 없었습니다. RECOVERY_TIMEOUT과 상승/하강·에어볼의 세부 경계는 자동 테스트에서 검증했으며 각각의 브라우저 수동 시나리오는 미검증입니다. 일반 창의 사람 수동 조작, 실제 GPU 성능 및 다른 브라우저도 별도 미검증입니다.

## 시선 방향과 우클 충전 패스

이전 플레이어 패스는 수평 속도 8m/s 고정이었고, 더미가 10m 안의 수평 조준 범위에 있을 때만 목표 캐치 높이를 계산했습니다. 필요한 수직 속도는 최대 3.5m/s로 잘렸으며 범위 밖에서는 1 - sin(pitch) * 2를 사용했습니다. 따라서 먼 더미에는 보조 범위 안에서도 공이 먼저 떨어질 수 있었습니다. 예를 들어 동일 높이의 단순 포물선에서는 수평 8m/s·수직 3.5m/s로 약 5.7m에 불과합니다(코드값에 따른 계산이며 측정값 아님).

이제 우클 누르기 → 놓기가 플레이어 패스 입력입니다. game-core의 startPassCharge로 시작하고 stepGame에서 passCharge를 누적하며 releasePass에서 발사합니다. 최대 충전 후에는 세기만 유지하고 자동 발사하지 않습니다. 슛 충전과 패스 충전은 서로 배타적입니다. 소유권 상실, Esc, blur, Pointer Lock 해제, R 초기화 시 충전을 취소하며 취소 후 mouseup이나 중복 release로 발사하지 않습니다. HUD는 패스 충전 중 **PASS POWER**, 백분율과 예상 발사 속도를 표시하고 슛의 PERFECT 구간은 숨깁니다.

court.ts의 PASS 초기 튜닝값:

| 설정 | 값 |
| --- | --- |
| minSpeed | 7m/s |
| maxSpeed | 22m/s |
| maxCharge | 1.2초 |
| releaseOffset | 카메라 조준선 앞 0.35m |

속도는 minSpeed + (maxSpeed - minSpeed) * clamp(passCharge / maxCharge, 0, 1)입니다. 이 범위는 게임 튜닝 설정이며 실제 측정 재질/투구 데이터가 아닙니다. 더미 반환 수평 속도는 PRACTICE.dummyReturnSpeed(8m/s)로 별도 관리합니다. 강한 정상 패스를 모두 거부하지 않도록 PRACTICE.catchSpeed를 28m/s로 조정했고, 높은 패스의 비행 여유는 passFlightSeconds 4초로 늘렸습니다. 자유 공의 발/몸통 획득 속도 설정은 변경하지 않았습니다.

렌더러 독립 방향 계산과 릴리스 계산은 packages/game-core/src/pass.ts에 있습니다. 기본 Babylon Scene은 왼손 좌표계이고 카메라는 rotation.set(pitch, yaw, 0)을 사용합니다. 설치된 targetCamera.js의 +Z 기준점과 RotationYawPitchRollToRef 구현을 확인했습니다. core 방향은 normalize(sin(yaw) * cos(pitch), -sin(pitch), cos(yaw) * cos(pitch))이며 양의 yaw는 오른쪽, 양의 pitch는 아래쪽입니다. 설치된 Babylon 변환 행렬과 직접 대조한 최대 성분 오차는 약 2.5e-8로 일치했습니다.

발사 순간의 시선만 사용하며 플레이어 패스에 더미 목표점 계산이나 수직 보조는 적용하지 않습니다. 카메라 높이 PLAYER.eyeHeight(1.7m)는 기존 CFG.eye와 공유합니다. 릴리스는 카메라 원점 + 방향 * 0.35m로, 카메라와 같은 직선에 있어 가까운 목표에 좌우 오프셋에 의한 시차를 추가하지 않습니다. 0.35m 안의 대상은 릴리스 공간에 너무 가까울 수 있으며 비행 중에는 중력으로 조준선에서 벗어납니다. 카메라 원점~릴리스 위치는 공 반지름을 고려한 기존 차폐 검사로 확인해 백보드/림 너머에 생성하지 않습니다. 기존 발사 후 자기 공 재획득 0.45초 제한은 유지합니다.

발사 후 속도는 중력·충돌에 의해서만 바뀌고 목표를 추적하지 않습니다. 더미의 반환 함수는 반환 순간 플레이어 위치를 별도로 계산합니다. 빗나간 패스는 바닥 접촉/비행 제한 후 자유 공이며 기존 회수와 경계/장기 방치 복구 정책을 사용합니다. 최대 패스 속도 22m/s는 기존 물리 한도 80m/s와 최대 192 substep 안에 있으며 실제 최대 세기에서 백보드·림 반사와 더미 캐치를 회귀 테스트합니다.

개발 F3 패널에는 최근 플레이어 패스의 세기·충전 시간·방향·릴리스 위치와 캐릭터 동작/드리블 주기/예약 발사/관절 수/공 Mesh 수도 표시합니다. 이 기록은 최초 발사 값을 보존하고 물리 적분으로 바뀌지 않으며 R로 초기화합니다. 기본/프로덕션 화면에는 노출하지 않습니다.

검증: 충전·수동 패스 테스트 20개를 추가해 기존 슛·획득·충돌·패스 시나리오와 합계 91개가 통과했습니다. npm run typecheck와 npm run build도 통과했습니다. yaw/pitch, 속도 증가/상한, 같은 각도의 도달 거리 차이, 최대 충전 유지, 취소/중복 release, 슛과 동시 충전 방지, 릴리스 시차/차폐, 강한 공의 백보드/림 반사와 더미 캐치, 통계 불변과 초기화를 포함합니다. 기존 패스 테스트는 충전/릴리스 API와 수동 조준에 맞춰 수정했고 슛·획득·충돌 규칙은 유지했습니다.

실제 브라우저: 기존 개발 서버를 임시 프로필의 headless Chrome + SwiftShader로 열었습니다. 약 4m 근거리에서 14.5m/s 패스, 약 11.1m 거리에서 최대 22m/s 패스 모두 더미 캐치 → 반환 → 플레이어 캐치가 확인됐습니다. 위/아래 pitch 입력에서 방향 y가 각각 +0.43/-0.43으로 기록됐고 화면에서도 비행을 확인했습니다. 최대 충전 100%에서 계속 눌러도 발사되지 않았으며 Esc·blur·Pointer Lock 해제 후 mouseup은 발사하지 않았습니다. 우클 메뉴 차단과 패스 후 점수 0·슛 통계 0/0 유지, 런타임 예외 없음도 확인했습니다. 일반 창의 사람 수동 조작, 실제 GPU 성능·다른 브라우저는 미검증입니다. 같은 각도의 정량 도달 거리 비교와 최대 속도의 충돌 경계는 자동 테스트로 검증했습니다.

## 관절형 캐릭터·드리블과 슛 폼

표시는 apps/web/game/createCharacter.ts로 분리했습니다. root → pelvis → torso → neck → head, torso → 좌우 shoulder → elbow → wrist, pelvis → 좌우 hip → knee → ankle 계층입니다. 뼈 사이 도형은 각 관절의 로컬 -Y 축에 연결되고 팔꿈치/무릎 pivot에서 실제 자식 관절을 회전시킵니다. 손마다 handSocket을 둡니다. 두 선분의 길이와 목표점에 따른 간단한 기하 계산만 사용하며 외부 모델·스켈레탈 리타게팅·IK 라이브러리나 범용 애니메이션 프레임워크는 추가하지 않았습니다.

기존 DUMMY의 1.8m 키, 머리·몸통·다리 폭과 비율을 재사용합니다. CHARACTER는 골반, 어깨, 위팔/아래팔, 손과 다리 분절·발 크기를 정의합니다. 더미 발바닥은 바닥 기준에 놓이며, 플레이어도 표시용 발 높이를 바닥에 맞춥니다. 1인칭에서는 머리·목만 숨기고 몸통·골반·팔·손·다리는 표시합니다. 몸통과 어깨는 조준 pitch로 회전시키지 않으며, 공 주변 손 목표를 팔 관절이 따라갑니다. 이 규칙은 온라인 상대 전신에도 동일하게 적용합니다. 기존 지상 슛의 무릎 굽힘과 점프 슛의 다리 펴기는 유지합니다.

게임 코어가 hand socket 목표, 동작 진행과 공 위치를 계산하고 View가 관절을 맞춥니다. 관절 위치를 읽어 소유권·득점·충돌·발사를 결정하지 않습니다. 관절별 물리 충돌체도 없습니다. 향후 스킨 모델로 교체할 때 같은 core pose를 표시 어댑터에 연결하면 되며, 향후 서버도 소유권과 실제 발사를 core에서 판정할 수 있습니다.

### Controlled ball과 동작

기본 소유 상태는 DRIBBLE입니다. 공은 손에서 바닥(바닥 높이 + 공 반지름, 현재 0.132m)으로 가속 하강하고, 바닥에서 속도 방향이 바뀌는 포물선형 상승으로 돌아옵니다. 바닥에서 완만해지는 sine wave를 사용하지 않습니다. 손이 공을 미는 구간과 떨어져 있는 구간을 구분하고 팔꿈치·손목이 이를 따라갑니다. 공은 기존 월드 ball Mesh 하나만 사용합니다. 손용 공을 따로 만들지 않습니다.

드리블은 소유자가 유지되는 controlled ball입니다. 손에서 떨어져 있어도 자유 공이 아니며 자유 물리, 줍기/패스 캐치, 득점과 자동 복구 경로에 들어가지 않습니다. 실제 릴리스 시점에만 소유자를 none으로 바꾸고 기존 자유 공 중력/충돌을 시작합니다. 이동 IDLE/MOVE는 공 동작과 별도로 관리해 모든 조합의 상태를 만들지 않습니다.

공 동작은 IDLE / DRIBBLE / CROSSOVER / GATHER / SHOT_CHARGE / PASS_CHARGE / RELEASE / CATCH입니다. 슛/패스 입력을 누르면 현재 드리블 위치에서 GATHER로 이어집니다. 바닥에 있던 공을 손으로 순간이동시키지 않습니다. 놓은 입력은 종류·충전량·yaw/pitch를 한 번 저장하며, Gather와 릴리스 이동이 끝날 때 실제 발사합니다. 짧은 클릭도 유실되거나 중복 발사되지 않습니다. 충전량은 버튼을 놓은 시점에 고정하며 그 뒤 동작 대기시간을 추가 충전으로 계산하지 않습니다. 실제 발사 위치는 그 순간 플레이어 위치와 저장한 조준에서 계산하고 손의 릴리스 기준과 일치합니다. 점수 구역도 실제 릴리스 순간 플레이어 위치로 결정합니다.

취소/소유권 상실/R 초기화는 예약 발사를 지웁니다. 취소 시 소유 공은 짧은 CATCH 보간으로 드리블에 복귀합니다. 캐치 성공도 실제 이동 구간 접촉점에서 시작해 손 쪽으로 가져오므로 즉시 보유 위치로 붙지 않습니다. 더미의 0.7초 보유 시간 안에 CATCH → DRIBBLE → GATHER → RELEASE를 배치해 별도의 반환 타이머가 중복 실행되지 않습니다. 반환 목표는 실제 릴리스 순간 플레이어 위치로 계산합니다.

### 사진 참고 슛 자세

보내준 사진처럼 슛 충전 중에 공을 머리 앞쪽으로 올리고, 오른손은 아래에서 받치고 왼손은 옆에서 보조하는 자세를 계속 유지합니다. 릴리스 때 오른팔을 펴고 손목을 꺾으며 가이드 손을 떼는 형태입니다. 이 슛 폼은 마우스를 누르고 있는 동안에도 1인칭 화면에 보입니다.

지상 슛 자세에서는 hip -0.28rad / knee +0.56rad / ankle -0.28rad의 굽힘과 골반 보정을 적용해 발바닥을 지면에 유지합니다. 점프 중에는 hip/knee/ankle를 0으로 펴고 상체 슛 폼을 유지합니다. 패스·드리블에는 이 슛 전용 하체 자세를 적용하지 않습니다. 새 손 기준과 맞추기 위해 슛의 실제 릴리스도 기존 눈 아래 위치에서 눈 위쪽 위치로 올렸습니다. 기존 충전/타이밍, 수평 조준·높이 보조, 탄도 계산과 1/2점 판정 규칙은 유지하고 새 시작 위치로 같은 탄도를 계산합니다.

### 검증과 제한

기존 규칙 테스트는 새 Gather/릴리스가 끝난 뒤 원래 발사 규칙을 검증하도록 조정했습니다. 모션 테스트 19개를 추가해 총 110개가 통과했습니다. 최종 npm run typecheck와 npm run build도 통과했고 / 및 /play 정적 출력을 생성했습니다. controlled 소유권·판정 제외, 바닥 접촉, 60/120Hz의 같은 시뮬레이션 시간, 짧은 입력, 충전 고정, Gather/Release 취소·소유권 상실·초기화, 더미 캐치·드리블·반환, 사진 기반 슛 폼 유지·지상 무릎 굽힘·공중 다리 펴기를 검사합니다.

추가 수치 검증은 node --import tsx scripts/verify-character.mjs로 실행합니다. 실제 Babylon NullEngine에서 캐릭터당 17개 관절의 부모 계층, hand socket 오차(최대 약 3.7e-7m), 1인칭 머리/몸통 숨김, 발바닥 지면 고정, 기본 키 1.8m와 월드 공 Mesh 1개, 지상 무릎/공중 직선 다리를 확인했습니다.

실제 headless Chrome + SwiftShader에서는 정지/이동/달리기 드리블 주기 0.84/0.62/0.46초, 상하 조준의 팔/공 연결, 짧은 패스 클릭, 점프슛, 근거리/약 11m 패스와 더미 왕복을 확인했습니다. 슛을 누른 동안 SHOT_CHARGE / SHOT FORM 1.00이 유지되고, 지상 무릎 0.56rad에서 점프 중 0rad로 전환됨을 화면과 진단에서 확인했습니다. 내려다본 화면에서도 하체가 표시됩니다. 공 Mesh 1개와 양 캐릭터 17개 관절이 유지되며 런타임 예외는 없었습니다.

현재 표현은 기본 도형과 절차적 두 분절 팔 계산입니다. 손가락·스킨 변형·정밀 인체 충돌·접촉력·범용 IK는 없습니다. 하체는 슛 굽힘/점프 펴기이며 보행 발 디딤 애니메이션은 아직 없습니다. 드리블은 자유 물리가 아닌 제어 궤적이며, 캐치 영역 가장자리/극단적인 조준에서는 손의 도달 길이를 제한해 짧은 보간 동안 공과 손 사이 간격이 보일 수 있습니다. 충전 중 공/팔이 화면 상단이나 주변을 일부 가리는 것은 자세 표현이며 카메라는 이동시키지 않습니다. 일반 창 사람 수동 조작, 실제 GPU 성능, 다른 브라우저와 모든 극단 각도 조합은 미검증입니다.

아래 도입 순서는 온라인 작업 이전의 설계 기록입니다. apps/game-server와 packages/protocol은 이제 실제 구현되었으며 현재 실행 방법은 문서 마지막의 온라인 테스트 절을 참조하세요.

- `apps/game-server` (향후): Colyseus 룸, 접속과 플레이어 수명 주기, 서버 틱, 입력 검증과 권위 상태 관리. `game-core`를 재사용하고 웹 렌더러를 참조하지 않습니다.
- `packages/protocol` (향후): 클라이언트·서버가 공유할 입력 메시지와 상태 동기화 타입. DOM/Babylon.js 및 Colyseus 서버 구현에 의존하지 않으며 게임 판정 규칙을 복제하지 않습니다.

도입 순서:

1. 실제 네트워크 구현 시 `apps/game-server`와 `packages/protocol`을 추가하고 npm workspace/package 경계와 실행 스크립트를 정합니다. 기존 웹 명령은 유지합니다.
2. 두 플레이어의 입력 메시지, 틱/순서와 동기화할 상태를 정의하고 서버에서 입력을 검증합니다. Colyseus 룸에서 `game-core`로 이동을 계산하고 웹에 상태 동기화와 상대 보간을 연결합니다.
3. 공·충전·슛·득점 판정까지 서버 권위로 이전합니다. 클라이언트는 입력을 보내고 서버 결과를 표시하며, 로컬 예측이 필요하면 같은 `game-core` 규칙을 사용해 서버 결과와 보정합니다.
4. 로그인/DB/소셜 로비는 이후에 도입합니다.

이전 검증 환경에서는 WebGL not supported 오류가 있었으나, 이번 로컬 headless Chrome에서는 SwiftShader로 3D 렌더링과 Pointer Lock 및 패스·회수를 확인했습니다. WebGL 지원 데스크톱의 일반 창에서 최종 수동 확인과 실제 GPU 성능 검증은 남아 있습니다.

## Q 드리블 손 전환과 V자 크로스오버

공을 소유한 지상 일반 드리블에서 Q를 누르면 반대 손으로 전환합니다. 기본 손은 오른손입니다. 키 자동 반복은 무시하며, 전환 중 새로 누른 Q는 다음 반대 방향 전환을 한 번 예약합니다. 예약이 이미 있으면 추가 입력은 버려 무한 대기열을 만들지 않습니다. 슛·패스 충전/Gather/공 미소유/공중에서는 새 전환을 시작하지 않습니다. F3 개발 패널에서 HAND, CROSS, CROSS PROGRESS와 수평 몸 방향을 확인할 수 있습니다. 일반 화면에는 Q 조작 안내만 표시합니다.

Q 입력은 WAIT_HAND_RETURN으로 예약됩니다. 현재 드리블 궤적의 남은 구간을 최대 0.18초 안에 진행해 다음 손 복귀 시점에 ACTIVE로 시작합니다. 공 위치를 순간이동시키지 않습니다. 실제 전환은 0.28초입니다. 전환 중 다시 누른 Q는 받은 손에서 즉시 반대 방향 V자로 이어지며 중간에 일반 드리블 한 주기를 기다리지 않습니다. 길게 누르기만 하면 자동 반복하지 않고, 눌렀다 떼는 입력마다 한 번 예약합니다. 공은 보내는 손 → 몸 앞 중앙 바닥 → 받는 손의 V자를 따릅니다. 바닥 중심 높이는 바닥 + 공 반지름(현재 0.132m)이며 접점에 머물지 않습니다. 완료 시에만 currentDribbleHand를 받은 손으로 확정하고 이후 드리블·캐치에도 유지합니다. R은 오른손으로 초기화합니다.

궤적과 동작 진행은 game-core의 motion.ts에서 계산하고 1인칭 팔과 더미 전신이 같은 characterPose를 사용합니다. 전환 중에도 controlled ball 소유권을 유지하며 자유 공 물리·획득·득점·복구에 들어가지 않습니다. 월드 공 Mesh는 기존 하나입니다. 보내는 팔의 안쪽 밀기, 받는 팔 준비, 손목과 작은 상체/무릎 이동을 표현하며 기존 팔 도달 길이를 제한합니다. 더미 자동 손 전환 AI는 없습니다.

수평 몸 방향은 시선 yaw를 초당 최대 4.5rad로 따라가므로 전환 도중 시선을 바꿔도 순간 회전하지 않습니다. 같은 방향을 평상시 드리블과 전환 양쪽에 사용합니다. 카메라를 움직이지 않으며 pitch는 바닥 궤적에 적용하지 않습니다. 공중 Q는 무시하지만 지상에서 이미 예약/시작한 전환은 점프 중에도 계속합니다. 손 높이는 연속적인 플레이어 높이를 따르고 바닥 접점은 월드 바닥에 고정합니다.

슛·패스 입력은 전환보다 우선하며 현재 공 위치에서 Gather로 연결합니다. 기존 짧은 클릭 예약 발사와 충전량·시선 방향을 유지합니다. 왼손 드리블도 양손 Gather를 거쳐 기존 오른손 슛 폼으로 연결합니다. blur/Pointer Lock 해제 등 기존 입력 취소 시 대기 예약을 지우며, 진행 중이면 현재 공 위치에서 기존 0.18초 CATCH 보간으로 복귀합니다. 중단한 전환의 손은 확정하지 않습니다. 소유권 상실과 R도 예약/진행 상태를 제거해 재개 후 뒤늦은 전환이 없습니다.

튜닝 위치는 packages/game-core/src/court.ts의 CROSSOVER입니다. duration 0.28초, maxReturnWait 0.18초, bounceFraction 0.48, contactForward 0.78m, maxYawRate 4.5rad/s, bodyShift 0.025m, kneeBend 0.06rad입니다. 양쪽 손 폭·전방 거리·높이는 DRIBBLE의 side 0.33m / forward 0.58m / idle·move·sprintHeight 1.20·1.15·1.08m를 재사용해 연결 경계를 맞춥니다. 모두 초기 표현 튜닝값이며 측정값이 아닙니다.

검증: 기존 110개를 유지하고 crossover.test.ts에 21개를 추가해 총 131개 테스트가 통과했습니다. 양방향·손 유지·반복 방지·상태별 거부·주기별 예약·바닥/소유권·점프·시선·짧은 슛/패스·취소/초기화·60/120Hz 결과를 검사합니다. npm run typecheck와 npm run build도 통과했습니다. scripts/verify-character.mjs는 실제 Babylon NullEngine에서 좌우 손 전환, 17관절, 공 Mesh 1개와 hand socket 오차 약 3.7e-7m 이하를 확인했습니다.

브라우저 검증: 실제 로컬 서버를 headless Chrome + SwiftShader로 열고 Q 양방향·키 반복 차단·걷기/달리기·상하 조준·전환 중 yaw 변경/점프·짧은 슛 1회/패스·왼손에서 오른손 슛 폼·blur/Pointer Lock 취소·더미 왕복 후 왼손 유지를 확인했습니다. 점수 0·패스 슛 통계 0/0, 공 Mesh 1개, 런타임 예외 0개를 확인했고 스크린샷도 확인했습니다. 일반 창에서 사람의 수동 조작, 실제 GPU 성능, 다른 브라우저와 모든 극단 시선 조합은 미검증입니다. 표현은 기존 기본 도형·기하 팔 맞춤이며 손가락/실제 인체 충돌은 없습니다. 급격한 시선 회전에는 몸 방향 지연 때문에 공이 일시적으로 시야 밖으로 나갈 수 있습니다.

이번 Q 작업 변경 파일: packages/game-core/src/court.ts, motion.ts, simulation.ts, 새 crossover.test.ts; apps/web/game/createCharacter.ts, createGame.ts; apps/web/app/Game.tsx; scripts/verify-character.mjs; README.md. 패키지와 lockfile은 유지했습니다.

## 오프라인 수비 연습

실행은 기존 `npm run dev:next`이며 Windows에서 필요하면 `npm.cmd`를 사용합니다. Esc로 Pointer Lock을 해제한 메뉴에서 시나리오를 선택하고 플레이합니다. R 또는 메뉴의 ‘현재 시나리오 재시도’는 선택한 시나리오의 월드 상태를 처음부터 다시 구성합니다.

| 시나리오 | 초기 상태와 동작 |
| --- | --- |
| A · 패스 연습 | 기존 플레이어 공 소유, 더미 캐치·드리블·자동 반환 유지 |
| B · 스틸 연습 | 더미가 공을 소유하고 고정 위치에서 플레이어를 보며 드리블. 반환 예약 없음. 접근해 공 쪽을 보고 좌클 |
| C · 블록 연습 | 더미가 골대를 향해 준비하고 2.5초 뒤 이상적인 충전량의 슛을 한 번 발사. 예고를 보고 우클. R로 같은 슛 재현 |
| D · 공격 자세 확인 | 플레이어 공 소유, 더미는 플레이어를 보며 수비 대기. 추적/자동 스틸/자동 블록 없음 |

공 소유 중 좌클 충전 슛, 우클 충전 패스, Q 연속 크로스오버는 유지합니다. 공이 없을 때 좌클 down은 스틸, 우클 down은 블록입니다. WASD/Shift/Space는 이동/달리기/일반 점프입니다. 버튼을 누른 채로 두어도 재발동하지 않습니다. 스틸과 블록은 동시 실행할 수 없고 회수 동작이 끝난 뒤에도 설정된 대기시간을 지킵니다. 입력 의미는 down 순간 소유권으로 고정되므로 스틸 성공 뒤 mouseup이 슛이 되지 않습니다. 공격은 새 down이 필요합니다. blur, Pointer Lock 해제와 모드 전환/초기화는 버튼 상태·충전·발사·전환 예약·블록 준비 점프를 정리합니다. 취소로 대기시간을 우회할 수 없고, 공중 블록 사용 이력은 착지까지 유지합니다.

### 판정과 표시 경계

`defense.ts`가 행동 시간·active 구간·손 판정 위치·성공/실패 사유를 계산합니다. `buttons.ts`는 입력 제스처, `practice.ts`는 시나리오 초기화와 예고/1회 발사만 담당합니다. 일반 슛의 기존 탄도 계산은 `shot.ts`로 추출해 플레이어와 더미가 공유합니다. 상태 원본은 기존 owner/flightKind이며 Babylon 관절이나 Mesh 충돌 결과를 읽지 않습니다. 기존 캐릭터 하나를 재사용하고 월드 공 Mesh도 하나입니다.

수비 기본 자세는 무릎과 골반을 낮추고 팔을 벌립니다. 이동 시 좌우/앞뒤 스텝을 적용하고 발목은 발 기울기를 보정합니다. 달리면 수비 웅크림을 부드럽게 해제하고 복귀합니다. 1인칭과 전신 모두 같은 core pose를 받습니다. 카메라 흔들림/강제 이동은 없습니다. 기존 A 모드의 더미와 플레이어 밀어내기는 보존했지만, B/C/D 모드에는 몸 충돌을 적용하지 않습니다.

스틸은 지상에서 시작하고 준비 → active → 회수로 진행합니다. active에서만 상대 소유 공의 실제 controlled 위치와 앞쪽 손 구를 비교하며 전방 각도와 기존 장애물 경로도 검사합니다. 성공하면 상대 Gather/충전·예약 발사를 취소하고 한 번만 소유권을 player로 바꾸어 CATCH → DRIBBLE로 연결합니다. MVP 스틸은 공을 자유 공으로 치는 대신 직접 획득합니다.

블록은 지상에서 준비 후 기존 점프 속도를 적용하며, 공중에서는 상승을 더하지 않고 팔 동작만 시작합니다. 한 번 공중에 있는 동안 active 구간을 재생성하지 않습니다. 비행 중인 무소유 슛/패스만 대상으로 공과 core 손 양쪽의 이동을 상대 swept sphere로 검사합니다. 기존 공 물리 substep의 충돌 보정 이후에 검사하며 관통 보정 경로는 블록 경로로 쓰지 않습니다. 손까지의 경로와 최종 밀어내기 경로도 기존 백보드·림 형상으로 확인합니다.

블록은 공을 소유하지 않고 접촉 법선으로 반사하며 작은 설정 충격을 더합니다. 같은 동작에서는 한 번만 충격을 주고 최대 속도를 제한합니다. 이후 중력·바닥·백보드·림 물리와 득점 정책을 계속 적용합니다. 블록했다고 무조건 실패로 확정하지 않고 이미 확정한 점수도 취소하지 않습니다. 블록한 상대 슛은 짧은 획득 제한 후 회수할 수 있으며, 그 외 상대 비행 슛에 별도 리바운드 규칙은 추가하지 않았습니다. C 모드의 슛 통계/점수는 더미의 연습 슛 결과를 포함하며 모드 전환으로 초기화됩니다. 골텐딩은 제외합니다.

## 이동·몸 충돌 후속 변경 (검증은 사용자 수행)

위의 테스트/브라우저 결과는 이전 수비 구현 시점의 기록입니다. 이번 이동·몸 충돌 변경은 사용자 요청에 따라 테스트, 타입 검사, 빌드, 브라우저 검증을 실행하지 않았습니다. 이번 변경에 대한 통과 결과나 측정 성능은 아직 없습니다.

원인: 기존 하체는 키 입력과 시계에 따른 작은 회전이었고, 공 소유 여부·충돌 후 이동량과 충분히 연결되지 않았습니다. 몸 충돌은 PASS 모드에서만 끝 위치를 밀어내는 방식이어서 다른 모드에서는 통과했고 큰 이동에는 연속 판정이 없었습니다.

### 설정과 속도

### 이동과 몸 충돌 정책

`bodies.ts`는 XZ swept circle로 고정된 사람과 코트 경계 중 가장 이른 접촉을 찾습니다. 접촉 직전까지 이동하고 남은 이동에서 안쪽 법선 성분만 제거해 접선 이동을 허용합니다. 이동 해결은 최대 8회이며 한도에 도달하면 남은 이동을 버립니다. 고정 더미는 밀리지 않습니다. 모든 연습 모드에 적용하며 점프 높이와 무관하게 수평 배타 영역을 유지합니다. 소유권/팔 자세/스틸·블록·캐치 영역은 몸 반경을 바꾸지 않습니다.

BODY.tolerance = 1e-6m, skin = 1e-5m입니다. 허용 중심 거리 하한은 반경 합 - tolerance이며, 정상 접촉은 skin만큼 앞에서 멈춥니다. 코트의 기존 root 이동 경계 X [-7.1, 7.1], Z [-7.0, 6.7]m를 같은 연속 해결기에 포함합니다.

초기 겹침은 이동 sweep과 별도로 최대 16회 복구하고 매번 모든 몸과 경계를 확인합니다. 중심 일치에는 결정적인 대체 법선을 사용합니다. 반복 복구가 실패하면 BODY.safe = (0, -6)m로 옮기며, 그 위치도 막혔다면 경계 안의 결정적인 0.30m 격자에서 유효한 위치를 찾습니다. 지원되는 안전 후보가 전혀 없으면 명시적인 RangeError로 잘못된 배치를 거부합니다. 복구로 이동한 거리는 보행 거리로 계산하지 않습니다.

현재 움직이는 사람은 플레이어 한 명이고 나머지는 고정 몸입니다. 여러 고정 몸을 처리하지만, 움직이는 사람끼리의 상대 이동/공정한 동시 해결은 구현·검증하지 않았습니다. 온라인, 접촉 밀치기, 파울, 스크린 AI도 추가하지 않았습니다.

`locomotion.ts`는 충돌 후 실제 수평 이동량으로 속도와 거리 기반 위상을 계산합니다. 실제 속도에 따라 보폭·진폭을 보간하고 정지 시 위상을 더 진행하지 않으며 자세 진폭은 감쇠합니다. 점프 중에는 보행을 중단합니다. `motion.ts`의 공 동작과 하체 진행은 분리되어 드리블·슛·패스·수비 팔을 보행이 덮어쓰지 않습니다. 기존 관절 표시에서 교차 다리, 골반, 무릎과 발목을 연결합니다. 발의 높이 보정은 단순 기하 계산이며 발 고정 IK/접촉 물리는 아닙니다. 카메라는 충돌 보정 좌표를 따르며 흔들림을 추가하지 않습니다.

## 선택 가능한 1인칭 카메라 흔들림

Esc 메뉴의 ‘카메라 흔들림’ 체크박스로 head bob을 켜고 끕니다. 기본값은 켜짐이며 R/시나리오 전환에도 선택을 유지합니다. 페이지를 다시 열면 설정 기본값으로 돌아갑니다. 끄기, 점프/공중, 포커스/Pointer Lock 해제, 초기화 시 시각 오프셋을 즉시 지워 잔여 흔들림을 남기지 않습니다.

설정은 `court.ts`의 HEAD_BOB입니다. 초기값은 enabled=true, 걷기 상하 0.01m·좌우 0.004m, 달리기 상하 0.02m·좌우 0.008m, smoothing=14/s, chargeScale=0입니다. 상하·좌우 진폭은 목표 진폭 설정이며 실측 결과가 아닙니다. smoothing은 지수 응답이고 화면을 보고 조절할 시작 값입니다.

walkPeriod/runPeriod는 좌우 한 쌍의 발 디딤 전체 주기(초)로, 기본값은 각각 1.35/2.45와 1.75/3.85입니다. GAIT.walkStride/runStride도 이 주기와 지상 속도에서 유도하므로 카메라만 별도의 시계로 앞서거나 뒤처지지 않습니다. 위상은 충돌 후 실제 이동 거리에서 계산하는 기존 locomotion.phase를 공유합니다. 한 쌍의 발 디딤 동안 상하는 두 번, 좌우는 한 번 움직입니다. 정지/몸·경계에 막히면 새 흔들림을 만들지 않고 기존 오프셋을 지수 감쇠해 기본 눈높이로 돌아옵니다. 실제 속도로 걷기/달리기 진폭을 보간하며 공중에는 보행 흔들림을 적용하지 않습니다. 착지 충격, roll, 강제 yaw/pitch는 없습니다.

`apps/web/game/cameraMotion.ts`가 렌더러 소유의 시각 오프셋만 관리합니다. 카메라 위치를 매 프레임 원래 눈 위치에서 새로 계산하며 player, 몸 실린더, ball, 입력 yaw/pitch, 발사 기준에 누적하지 않습니다. 기본 충전 감소 배율 0은 슛/패스 충전과 Gather 동안 완전 억제해 중앙 조준과 원래 발사 광선을 일치시키기 위한 선택입니다. 배율을 0보다 크게 조정하더라도 실제 release 예약/동작 때는 오프셋을 반드시 제거합니다. mouseup으로 release가 예약될 때도 잔여 값을 지웁니다. 실제 공 생성 위치와 기존 장애물 검사는 변경하지 않았습니다. 시각 눈 위치까지의 이동 자체도 기존 백보드/림 경로 검사로 보수적으로 제한합니다.

직접 확인: 걷기와 Shift 달리기의 미세한 상하/좌우 차이 → E/F/G 모드에서 몸/경계에 막혔을 때 눈높이 복귀 → Space 공중의 흔들림 중단 → 이동 중 슛/패스 충전 시 흔들림 억제 → 짧은 클릭 릴리스와 백보드 근처 발사 차단 → Esc에서 켜기/끄기 뒤 오프셋이 남지 않는지 순서로 확인하세요. 화면 중앙 조준선, 플레이어 위치, 충돌 거리와 공 발사가 설정 켜기/끄기에 영향을 받지 않아야 합니다.

발 디딤과 카메라의 공통 cadence도 실제 이동 속도에서 유도하고 지수 응답을 적분해 걷기↔달리기 주기가 갑자기 바뀌지 않도록 했습니다. 실제 이동이 0이거나 공중이면 위상은 진행하지 않습니다. 주기 변경은 표시용 보행 정보에만 영향을 주며 이동·몸 충돌·공 발사는 변경하지 않습니다.

이번 카메라 변경 파일: `court.ts`, `locomotion.ts`, 새 `apps/web/game/cameraMotion.ts`, `createGame.ts`, `apps/web/app/Game.tsx`, `globals.css`, `README.md`. 사용자 요청에 따라 테스트·타입 검사·빌드·브라우저 검증을 실행하지 않았습니다. 위 항목은 확인 방법이며 통과 결과가 아닙니다.

## 두 사람 온라인 테스트 (현재 버전)

기존 오프라인 모드 A~G는 유지합니다. 온라인은 **두 명의 자유 연습 코트**이며 정식 1v1/승패/공격 교대/제한시간은 없습니다. 온라인은 더미와 자동 반환 패스 없이 두 참가자와 공 하나만 존재합니다. 서버는 별도 Node.js 프로세스이므로 정적 웹 배포에 포함되어 실행되지 않습니다. 이번 작업은 로컬 실행까지만 수행했습니다.

### 설치와 Windows 실행

기존 npm과 package-lock.json을 사용합니다. [공식 0.17 마이그레이션 문서](https://docs.colyseus.io/migrating/0.17)의 서버·SDK 0.17 / Schema 4 호환 계열을 확인했고, 실제 설치 API 선언과 통합 테스트로 연결을 확인했습니다. 설치 버전은 core 0.17.56, SDK 0.17.43, Schema 4.0.31, ws-transport 0.17.13입니다. 전송 패키지가 사용하는 Express도 명시적으로 설치했습니다.

```powershell
npm.cmd ci
# 기존 .env.local이 있다면 덮어쓰지 말고 필요한 항목만 수정합니다.
Copy-Item apps/web/.env.example apps/web/.env.local

# 터미널 1: 게임 서버 (기본 127.0.0.1:2567)
npm.cmd run dev:server
# 터미널 2: 웹 (기본 0.0.0.0:3000)
npm.cmd run dev:next
```

두 서버를 모두 종료한 상태에서는 `npm.cmd run dev:online`으로 함께 실행할 수도 있습니다. 이미 같은 프로젝트의 Next 개발 서버가 실행 중이면 추가 웹 서버를 실행하지 말고 기존 주소를 사용하세요. 서버 코드를 수정했다면 게임 서버를 다시 시작합니다.

웹 환경 파일은 `apps/web/.env.local`이며 `NEXT_PUBLIC_GAME_SERVER_URL=ws://127.0.0.1:2567`을 설정합니다. 주소가 없으면 온라인 진입 시 명시적으로 오류를 표시하고 오프라인은 계속 사용할 수 있습니다. 클라이언트 연결 코드에는 localhost 기본 주소를 숨겨 두지 않았습니다. NEXT_PUBLIC 값은 웹에 공개되는 서버 주소이며 비밀값이 아닙니다. 변경 후 웹 서버를 재시작/재빌드합니다.

서버 환경 변수는 `GAME_SERVER_HOST`(기본 127.0.0.1), `GAME_SERVER_PORT`(기본 2567)입니다. PowerShell에서 실행 전에 설정하며 서버가 웹의 .env.local을 읽는 것은 아닙니다.

```powershell
npm.cmd run typecheck        # 웹과 서버 모두
npm.cmd test                 # 기존 오프라인 + 온라인 코어
npm.cmd run test:server      # 실제 Colyseus 서버/SDK 통합
npm.cmd run build            # 웹 정적 출력 + 서버 번들
node apps/game-server/dist/server.mjs
```

`build:web`, `build:server`, `typecheck:web`, `typecheck:server`도 개별 실행할 수 있습니다. 서버 번들은 별도 프로세스로 실행하고 npm 의존성이 필요합니다. 기존 `dev:next`, `test`, `typecheck`, `build` 진입 명령을 유지했습니다.

### 같은 PC / 같은 Wi-Fi / 인터넷

같은 PC에서는 일반/시크릿 창 또는 브라우저 두 개로 웹 주소를 엽니다. 첫 화면의 ‘방 만들기’를 누르고 표시된 Room ID를 복사합니다. 두 번째 화면에 그 ID를 입력하고 ‘Room ID로 참가’를 누릅니다. 각 화면의 ‘코트에서 플레이’로 마우스를 잠급니다. 방이 꽉 찼거나 ID가 틀리면 오류를 표시하며 자동으로 다른 방을 만들지 않습니다. Esc 메뉴의 ‘온라인 나가기’로 퇴장하고 남아 있는 Room ID에 새 참가자로 다시 들어갈 수 있습니다. 마지막 사람이 나간 방은 없어지므로 그 뒤에는 새 방을 만들어야 합니다. R은 온라인 월드와 점수를 초기화하지 않습니다.

같은 Wi-Fi의 두 PC에서는 호스트의 LAN IP(예: 192.168.0.20)를 사용합니다.

```powershell
# 호스트: 서버가 LAN 연결도 받도록 설정
$env:GAME_SERVER_HOST='0.0.0.0'
npm.cmd run dev:server
```

웹 개발 서버는 기존 실행 스크립트에서 0.0.0.0에 바인딩합니다. 호스트의 웹 .env.local을 `NEXT_PUBLIC_GAME_SERVER_URL=ws://192.168.0.20:2567`로 수정하고 웹을 다시 시작합니다. 두 PC 모두 `http://192.168.0.20:3000`으로 접속합니다. 상대 PC의 localhost는 상대 PC 자신이므로 사용하지 않습니다. 방화벽 전체를 해제하지 말고 신뢰하는 개인 LAN에서 TCP 3000/2567 등 실제 사용 포트만 허용하세요. 관리자 PowerShell에서 필요한 경우 다음처럼 개인 프로필로 한정할 수 있습니다. 이 명령은 이번 작업에서 실행하지 않았습니다.

```powershell
New-NetFirewallRule -DisplayName 'CheckTheBall LAN dev' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 3000,2567 -Profile Private
```

원격 LAN의 일반 HTTP에서는 Pointer Lock 등 브라우저 API가 브라우저/권한 설정에 따라 제한될 수 있습니다. 해당 브라우저에서 확인하고 필요하면 두 기기에서 신뢰하는 인증서를 사용하는 HTTPS 개발 프록시를 준비하세요. HTTPS 페이지에는 WSS 게임 서버 주소가 필요합니다. TLS 프록시/인증서 설치나 외부 공개 배포는 수행하지 않았습니다. localhost/LAN 설정만으로 인터넷 친구가 접속할 수 있는 것은 아닙니다.

### 서버 권위와 프로토콜

`BasketballRoom`은 참가자 최대 2명, 시뮬레이션 60Hz, 상태 전송 20Hz입니다. 물리 틱은 기존 1/60초이고 공의 bounded substep은 유지합니다. 콜백 지연은 작은 고정 틱으로 분할하고 한 콜백에 최대 8회만 따라잡아 큰 dt를 공 물리에 직접 넘기지 않습니다. 클라이언트 이동 heartbeat는 최대 30Hz입니다.

`packages/game-core/src/online.ts`의 OnlineWorld가 **공 State 하나와 참가자별 개인 동작 상태**를 관리합니다. 기존 규칙을 호출할 때만 같은 State에 참가자 관점을 연결하며 참가자마다 stepGame을 실행하거나 공 물리를 여러 번 계산하지 않습니다. DOM/React/Babylon을 서버에서 import하지 않습니다. 클라이언트 `actorView`는 표시용 상태를 조립할 뿐 규칙을 진행하지 않습니다.

입력은 seq, 이동 축, sprint, yaw/pitch와 행동 의도만 전송합니다. 위치·공 속도·소유권·충전 시간·성공 여부·점수는 받지 않습니다. 허용되지 않은 필드, 비유한 숫자, 축 [-1,1] / yaw [-π,π] / pitch [-1.2,1.2] 이탈, 역행/중복 seq는 거부합니다. 입력 JSON 상한 2048자, 소켓 수신 상한 4096바이트, 메시지당 행동 8개, 대기 행동 32개, 참가자당 초당 100메시지 제한입니다. 메시지를 많이 보내도 시뮬레이션 시간이 더 진행되지 않습니다.

이동은 최신 유효 입력, 행동은 도착 순서대로 한 번 처리합니다. 행동에는 당시 yaw/pitch를 따로 저장해 이후 heartbeat가 release 방향을 덮어쓰지 않습니다. 충전은 서버 틱 시각의 시작/종료 차이로 계산합니다. 같은 틱의 down/up은 충전 0의 최소 세기 릴리스 한 번을 Gather 후 실행합니다. 소유권 세대 번호가 달라진 오래된 up은 새 슛/패스를 만들지 않습니다. 600ms 동안 입력이 없거나 취소 의도가 오면 이동과 충전·예약 동작을 정리합니다. blur/Pointer Lock 해제도 중립+취소 입력을 보냅니다. 모든 판정은 현재 서버 상태이며 지연 보상/되감기는 없습니다.

첫 참가자만 최초 공을 받습니다. 소유권 변경은 하나의 ownerId로 처리하며 controlled 드리블·크로스오버는 자유 공이 아닙니다. 패스는 슛 통계/점수를 바꾸지 않고 상대 캐치로 연결됩니다. 동시에 공을 얻을 수 있으면 서버 틱 홀짝에 따라 참가 슬롯 검사 순서를 번갈아 적용합니다. 매번 첫 참가자가 우선하는 정책은 아닙니다.

서버 몸 충돌은 두 사람의 상대 이동을 한 번에 sweep하고 각자의 안쪽 이동 성분만 제거합니다. 한쪽을 먼저 고정 처리하지 않으며 정지한 상대를 밀어내지 않습니다. 기존 반경 0.30m, tolerance 1e-6m, skin 1e-5m와 점프 중 수평 배타 규칙을 유지합니다. 코트 경계를 함께 제한하고 최대 8회 후 남은 이동을 버립니다. 잘못된 두 사람 겹침은 고정 안전 쌍 (-1,-1.5)/(1,-1.5)m으로 복구합니다. 참가/재참가 위치는 기존 참가자와의 겹침 복구를 거쳐 정합니다. 다중 서버/3명 이상 동적 몸 해결은 범위 밖입니다.

스틸과 블록은 기존 config/active/재사용 대기/장애물 조건을 재사용합니다. 스틸은 상대 Gather·충전·예약을 취소하고 직접 캐치로 연결합니다. 블록은 소유권을 주지 않고 공을 반사하며 모든 참가자에게 0.25초 획득 제한을 적용합니다. 한 행동의 중복 충격을 막고 득점 자격은 유지합니다. 슛에는 release 당시 shooterId를 남기며, 소유권 변경/블록/퇴장 뒤에도 그 ID로 점수를 귀속합니다. 떠난 참가자의 점수 기록은 Room 내 ledger에 보존하므로 뒤늦은 득점도 오류 없이 전체 점수에 반영합니다. 이미 확정한 득점은 다시 처리하지 않습니다.

퇴장한 캐릭터는 제거하고, 소유 중이던 공은 마지막 위치에서 무소유 자유 공으로 해제합니다. 이미 비행 중인 공과 점수는 유지합니다. 새 참가자는 공 없이 빈 슬롯에 들어옵니다. 재접속 복원은 없으며 마지막 퇴장 시 Colyseus autoDispose가 타이머와 Room을 정리합니다.

### 표시와 남은 한계

Colyseus Schema는 tick과 원자적인 JSON 스냅샷 envelope를 전송합니다. 이번 소규모 버전에서는 개인별 관절 각도 대신 위치·입력 시선·동작 종류/경과 시간·드리블 위상 등 기존 core 동작 정보를 보냅니다. 전체 JSON envelope 패치이므로 대규모/대역폭 최적화용 구조라고 주장하지 않습니다.

위치·상대 시선·점프·공은 약 100ms 스냅샷 버퍼로 같은 렌더 시각에 보간합니다. 소유권/캐치/릴리스/블록/복구 revision이 바뀌면 공을 이전 소유자에서 새 소유자로 가로질러 보간하지 않습니다. 내 마우스 시선은 즉시 반응하지만 내 이동은 서버 상태를 보간해 표시합니다. 이것은 입력 예측이 아니며 Client Prediction/Reconciliation은 없습니다. 기존 관절형 1인칭/전신과 슛·수비 자세를 재사용합니다. head bob은 로컬 시각 오프셋이고 서버 판정에 쓰이지 않습니다.

인터넷 지연에서는 이동 반응이 늦고 빠르게 움직이는 상대에 대한 스틸/블록이 로컬 화면 예상과 다를 수 있습니다. 로그인·DB·Redis·로비/자동매칭·정식 경기 규칙·파울/골텐딩·지연 보상·재접속 복원·다중 서버·부하 테스트는 제외했습니다.

### 온라인 실제 검증과 변경 파일

실제 로컬 Colyseus 서버와 SDK 두 개로 같은 방 참가, 세 번째 거부, 이동/점프, 패스/캐치, 서버 충전·1회 발사, 잘못된 입력·중복 seq·타임아웃, 스틸 후 예약 취소, 단일 자유 공 획득, 블록·슛 귀속·중복 득점 방지, 퇴장/자리 재사용, 마지막 퇴장 후 방 삭제를 검증했습니다. 코어 테스트는 상대 이동 sweep 대칭성·공중 충돌·고속 교차 방지와 동시 획득 순서 교대도 포함합니다.

### 고정 입력·예측·보정 규약

- 일반 seq는 메시지의 수신 순서이고 기존 ack는 마지막 수신 승인입니다. **processedInputSeq**는 마지막으로 이동에 반영한 메시지 seq, **processedMoveSeq**는 마지막 처리 이동 프레임 번호입니다. 행동 완료 번호는 processedActionSeq로 별도 관리합니다. 예측 재생에는 수신 ack를 사용하지 않습니다.
- 새 클라이언트는 60Hz의 moveSeq 프레임을 만들고 서버는 60Hz 틱당 최대 한 프레임을 소비합니다. 이동 프레임이 없는 틱에는 마지막 이동 축을 중복 적용하지 않습니다. 수직 운동은 서버 고정 틱에서 계속 처리합니다. 프레임에 클라이언트 위치나 임의 dt는 넣지 않습니다.
- 이동·점프 적분은 공통 movement.ts의 integrateMovement를 서버와 클라이언트가 공유합니다. 기존 속도·충전 감속·공중 감속·중력·실린더 규칙을 재사용합니다. 공·점수·스틸/블록 판정은 예측하지 않고 서버가 결정합니다. 블록의 도약 예약은 서버 행동 상태를 따르며 별도 로컬 블록 점프를 중복 생성하지 않습니다.
- 새 권위 상태 수신 시 권위 위치/수직 속도로 논리 위치를 즉시 맞추고, processedMoveSeq 이후의 미확인 이동 프레임을 한 번씩 재생합니다. 자기 위치에는 상대용 100ms 지연을 적용하지 않습니다. 상대와 비행 공은 기존 지연 보간을 유지합니다. 소유 공의 로컬 표시 기준만 자기 예측 위치에 연결하며 소유권/공 속도/발사 판정은 서버에 남습니다.
- 상대 충돌의 로컬 예측은 최신 권위 상대 위치를 고정한 보수적인 proxy를 사용합니다. 서버는 두 사람의 상대 이동을 함께 해결합니다. 접촉 때에는 상대 이동을 미리 알 수 없으므로 추가 보정이 생길 수 있고, 이것을 지연 보상이나 완벽한 원격 예측이라고 부르지 않습니다.
- 0.0001m 이상 재생 오차는 보정 횟수에 기록합니다. 논리 보정을 끝낸 뒤 **8cm 미만**의 작은 잔여 시각 오차만 response 14/s로 감쇠합니다. 잔여 누적도 8cm로 제한하고 큰 보정은 즉시 적용합니다. 강한 lerp로 계속 틀린 논리 위치를 감추지 않습니다.
- 서버 대기 이동은 32개, 클라이언트 미확인 이동은 64개로 제한합니다. 로컬 한 번의 입력 타이머에서 최대 4 fixed step만 생성합니다. 250ms 초과 공백/대기열 포화/과도한 catch-up은 중립 취소 후 새 권위 확인을 기다리며 오래된 입력을 몰아서 실행하지 않습니다.
- blur/Pointer Lock 해제의 cancel은 이동 취소 경계입니다. 서버는 그때까지 받은 미소비 이동도 버리고 처리 번호로 확인합니다. 클라이언트도 과거 프레임을 지우고 취소 확인 이후 새 입력을 시작합니다. 탭 복귀에 이전 이동이 재생되지 않도록 합니다.

### F3 진단 읽기

개발 모드에서 F3를 열면 프레임·보정 카운터를 새로 시작합니다. 상세 진단은 약 200ms 간격으로 갱신하며 카메라 갱신과 연결하지 않습니다.

| 표시 | 의미 |
| --- | --- |
| FRAME avg/max, long>=50 | 렌더 프레임 간격 평균/최대와 50ms 이상 긴 프레임 수 |
| RENDER max | 한 렌더 호출의 최대 소요 시간. 실제 GPU 성능 전체를 뜻하지 않음 |
| mouse/frame, angle, LOCAL yaw/pitch | 해당 프레임의 마우스 이벤트 수, 로컬 각도 변화량과 시선 값 |
| LOCAL camera error | 적용한 카메라 각도와 로컬 입력 각도의 차이. 서버 시선과의 차이가 아님 |
| LOOPS | 캔버스에 등록된 활성 게임 런타임 수. 정상 목표는 1 |
| tick / processedInput / processedMove / receiveSeq | 수신 서버 틱·실제 처리 이동 확인·수신 승인 구분 |
| PENDING / staleDrops | 미확인 이동 프레임 개수 / 버린 중복·역행 스냅샷 수 |
| ERROR server / afterReplay | 예측 위치 대 원시 서버 위치 차이 / 미확인 입력 재생까지 끝낸 실제 보정 차이. 전자는 지연만으로도 생길 수 있음 |
| CORRECTIONS / last / resets | 실제 보정 횟수·최근 보정 거리·권위 초기화 횟수 |
| PRED / AUTH, SERVER LOOK | 예측 위치/원시 서버 위치와 서버가 받은 시선. 카메라에 서버 시선을 적용하지 않음 |
| VISUAL / WRITE | 작은 시각 잔여 거리와 현재 논리 위치 변경 경로 |
| SERVER / overlapRecoveries | 서버 위치 적용 경로와 겹침/안전 복구 횟수 |

### 직접 확인할 시나리오

웹/게임 서버 재시작 후 새 Room에서 같은 해상도·브라우저·그래픽 설정으로 각 항목을 약 10초씩 기록하세요. 항목을 바꿀 때 F3를 닫았다 열어 카운터를 초기화합니다. head bob 켜기/끄기 조건도 수정 전후 동일하게 맞춥니다.

1. **혼자 입장, 정지 후 마우스만 회전**: FRAME max/long과 mouse/frame·angle·camera error를 같이 봅니다. 긴 프레임이 늘면 렌더/메인 스레드 부하, 프레임은 정상인데 각도만 계단식이면 입력 전달 경로를 의심합니다. 서버의 SERVER LOOK이 늦어도 로컬 시선이 그 값으로 되돌아가면 안 됩니다.
2. **혼자 이동/정지/Space 점프**: processedMove가 진행하고 PENDING이 끝없이 커지지 않아야 합니다. 멀리 떨어진 상대가 없는데 afterReplay/보정 횟수가 계속 크게 늘면 단순 지연으로 넘기지 말고 기록하세요. 멈춘 뒤 과거 좌표로 주기적으로 왕복하지 않아야 합니다.
3. **두 명이 떨어져 이동**: 자기 이동은 즉시, 상대는 지연 보간으로 표시되는지 확인합니다. 서버/클라이언트의 동일 fixed step, 속도와 ack 규약 확인 대상입니다.
4. **두 명이 정면 접촉·옆으로 돌아가기**: 서버 반경 합 0.60m의 수평 배타가 점프 중에도 유지되어야 합니다. 접촉 보정과 겹침 복구 카운터를 구별하세요. 정상 접촉을 계속 밀 때 안전 위치로 순간이동하거나 overlapRecoveries가 반복 증가하면 해당 수치를 기록합니다.
5. **탭 전환 후 복귀**: Pointer Lock을 다시 잡아도 과거 입력이 몰아서 실행되지 않아야 합니다. 취소/권위 reset 증가 한 번과 계속 반복되는 보정은 구별합니다. LOOPS가 늘어나지 않는지도 확인합니다.

각 시나리오의 수정 전/후 FRAME avg/max/long, camera error, PENDING 범위, afterReplay, 보정 횟수 증가량, overlapRecoveries 증가량을 나란히 남기면 됩니다. 이번 작업에서는 어느 항목도 실측하지 않았습니다. 명령 검증이 필요하면 사용자가 npm test / npm run test:server / npm run typecheck / npm run build를 실행합니다.

이번 수정 파일: protocol/index.ts, game-core의 online.ts/bodies.ts 및 새 movement.ts, 웹의 onlineClient.ts/createGame.ts/Game.tsx/globals.css 및 새 movementPrediction.ts/frameDiagnostics.ts, README.md. 기존 오프라인 실행 경로와 서버 공 판정은 유지했습니다. 새 예측·보정과 보간 변경은 실행 검증 전입니다.

### 방 생성 직후 규약 오류로 종료된 원인

2026-11-05 확인 당시 2567 포트를 점유한 프로세스는 이전 작업에서 남은 게임 서버(PID 38076, tsx 부모 29200, 오전 1:29 시작)였고, 웹 서버는 이후 새로 시작되어 있었습니다. 기존 서버 두 프로세스만 종료했고 웹 서버는 유지했습니다. 소스는 v2지만 남아 있는 프로세스는 재로딩하지 않아 새 웹과 규약이 달랐습니다. 기존 dist/server.mjs에도 v2 정보가 없어 이전 빌드 실행 시 같은 오류가 날 수 있었습니다.

### 입력 적체·취소·위치 보정 진단 (2026-11-05, protocol v3)

기존 구조에서 프레임/입력 펌프 지연과 미확인 입력 초과가 전체 cancel을 보내
이동 큐와 슛·패스 충전을 함께 지웠다. 서버 큐 초과 시 새 이동을 거부하는 경로도
ACK 정체를 유발할 수 있었다. 코드와 회귀 테스트로 확인한 경로이며 실제 사용자
환경에서 발생한 사유별 빈도와 수정 전후 체감은 미측정이다.

변경 순서: 원인별 진단 추가 → 이동 재동기화와 행동 취소 분리 → 유한 큐/ACK 규약
적용 → 클라이언트 재생 검증. 기존 시선·공·몸 충돌 판정 구조는 유지한다.

입력/ACK 규약:
- moveSeq 하나는 고정 1/60초 이동 1회다. 서버는 틱당 최대 하나만 실행한다.
- ack는 수신한 메시지 seq이며 실행 확인이 아니다.
- processedMoveSeq는 실행 또는 명시적 폐기를 마친 연속 구간의 마지막 번호다.
  processedInputSeq는 해당 이동 메시지 seq, processedActionSeq는 처리한 행동 seq다.
- 클라이언트는 processedMoveSeq보다 큰 미확인 이동만 서버 위치 위에서 재생한다.
- 서버 큐는 12개로 제한한다. 넘치면 오래된 이동부터 폐기하고 최신 입력을 받는다.
  수신 후 서버 시뮬레이션 시간으로 200ms 넘게 대기한 이동도 폐기하고 ACK한다.
  이동에 포함된 점프도 함께 폐기하되 별도 슛/패스 행동은 지우지 않는다.
- 큐가 비면 수평 이동을 멈춘다. 마지막 입력을 무한 유지하지 않는다.
  네트워크 변동에 따른 빈 큐 정지를 이번 변경으로 완전히 없앴다고 주장하지 않는다.
- PUMP_GAP(250ms), CATCH_UP_LIMIT(약 83ms), PENDING_LIMIT(64개)은
  movementSync로 이동만 재동기화한다. 충전·버튼·릴리스 예약은 유지하고 ACK 후 새 이동을 시작한다.
- Esc/blur/Pointer Lock 변경은 명시적 cancel을 유지한다. 입력 무응답 600ms도
  안전 취소하되 매 틱 반복 계수하지 않는다. 실제 무응답 취소는 충전을 종료한다.
- 자기 yaw/pitch는 로컬 입력으로 표시하며 서버 위치 보정이 덮어쓰지 않는다.

개발 서버에서 F3로 생성/수신/소비율, 큐 길이/나이, cancel·sync 사유별 횟수,
서버 틱 CPU 시간, ACK와 위치 보정을 확인한다. 콘솔에서 다음 명령으로 최근 최대
600개 시계열 기록을 복사한다. 매 프레임 콘솔 로그와 React 갱신은 추가하지 않았다.

```js
copy(JSON.stringify(window.checkTheBallNetwork(), null, 2))
```

각 기록의 at는 epoch ms, clientMs는 클라이언트 단조 시각이다. snapshot, cancel,
movementSync, longFrame(50ms 이상) 이벤트에 프레임/렌더 시간, ACK 진행량,
미확인 입력 나이와 보정 거리를 남긴다. server에는 수신/소비/폐기 계수와 timeout
횟수·마지막 사유·발생 시각이 포함된다. 서로 다른 장치의 epoch 시각은 시계 오차에 주의한다.

rate는 약 1초 구간의 클라이언트 수신 기준 속도로 순수 서버 처리 성능 측정치가 아니다.
서버 oldestAgeMs는 수신 후 큐 대기시간이며 인터넷 전송시간을 포함하지 않는다.
클라이언트 oldestPendingMs는 ACK를 기다린 전체 시간이다. tickMs/maxTickMs는
world.step 실행 소요시간, callbackGapMs는 콜백 간격, discardedTimeMs는
150ms 콜백 제한으로 버린 누적 시간이다. 설정은 packages/protocol/src/index.ts에 있다.

동일 재현 시나리오(각 20초): 혼자 정지·시선 회전 → 이동·정지·점프 → 이동하며
슛/패스 충전 → 두 명 떨어져 이동 → 정면 접촉 → 탭 전환/복귀.
같은 브라우저·해상도·head bob 설정에서 사유/시각과 frameMs, tickMs, ACK 진행,
큐 나이, correction을 대조한다. 탭 전환의 HIDDEN/BLUR 취소와 이동 재동기화를 구별한다.
수정 전 런타임 기록은 확보하지 못했으므로 지연 감소율이나 체감 개선 수치는 제시하지 않는다.

실제 실행 결과: npm.cmd test 174개 통과(실패 0), npm.cmd run test:server 3개 통과
(실패 0), npm.cmd run typecheck 웹·서버 통과, npm.cmd run build 웹·서버 통과.
최종 진단 코드 뒤 클라이언트 복구 테스트 4개(174개에 포함)와 타입 검사도 재확인했다.
브라우저 실기 및 실제 서버 부하·수정 전후 시계열 비교는 미측정이다.
protocol v3 적용 시 웹과 게임 서버를 같은 소스로 실행하고 두 클라이언트를 새로 연결한다.

### 온라인 개인 점수판·효과음 (protocol v4)

상단 중앙 점수판은 session ID로 나/상대를 찾는다. 내 점수는 항상 왼쪽이며 YOU를
표시한다. 닉네임은 접속 메뉴에서 선택적으로 입력하며 비어 있으면 나/상대를 쓴다.
서버 개인 점수를 즉시 표시하고 점수가 증가한 기존 참가자만 650ms 강조한다.
새 참가자의 기존 점수는 강조하지 않는다. 공 소유자·상대 대기 상태를 표시한다.
퇴장한 ID의 기록은 기존 ledger 정책을 유지하고 새 ID로 재참가하면 개인 점수 0이다.
자유 연습이므로 승리·경기 종료는 없다. HUD는 기존 변경 감지/주기 갱신을 유지한다.

오디오는 전용 `apps/web/game/audioManager.ts`의 Web Audio 경로 하나를 사용한다.
Babylon 8.56.2 설치와 AudioV2 API 존재를 확인했고 공식 문서도 확인했다:
https://doc.babylonjs.com/features/featuresDeepDive/audio/playingSoundsMusic/
Babylon 오디오 엔진은 별도로 켜지 않는다. 런타임당 AudioContext 하나, 디코딩한
버퍼 하나씩을 재사용하고 gain/pan 슬롯 12개로 동시 재생을 제한한다.
Web Audio의 일회용 BufferSource는 재생할 때만 생성하며 프레임마다 만들지 않는다.

실제 자유 공 바닥/림/백보드 충돌은 physics의 관찰 콜백으로 기록하며 판정 결과를
바꾸지 않는다. 블록 타격은 실제 tryBlock 성공 때만 기록한다. 서버 득점 경로에서
네트 사건을 한 번 만들고 shotId별 림/보드 접촉 이력을 함께 보낸다. 패스/화면의 점수
변화로 소리 계층이 득점을 다시 판정하지 않는다. 점프/블록 점프/착지도 서버 확정이다.
내 점프음은 예측하지 않으므로 통신 지연이 있을 수 있지만 재생 중복은 없다.

각 사건은 eventId, serverTick/time, actorId, shotId/actionId, 위치, 세기를 담는다.
Room의 기존 JSON snapshot에 최근 2초·최대 128개만 넣는다. Schema 배열을 무한히
늘리지 않는다. 클라이언트는 최초 수신의 과거 사건을 건너뛰고 단조 eventId와 최대
512개/5초 중복 기록으로 재생을 제한한다. 예약은 최대 128개·1초이며 표시 시점보다
180ms 넘게 늦으면 버린다. 공/상대는 기존 보간 시각, 내 확정 점프는 최신 서버 시각을
사용한다. 한 패킷으로 접촉·네트 사건이 늦게 함께 도착하면 최대 30ms 간격을 보조한다.

내 드리블·발자국은 내 표시 모션, 상대는 보간 모션의 주기 경계에서만 발생한다.
공중/Gather에는 바운드음이 없고, 발자국은 접지·실제 이동 거리/속도가 필요하다.
입력 재생 함수에는 오디오 부작용을 넣지 않았다. 220ms 이상 표시 공백이면 지나간
주기를 따라 재생하지 않는다. 탭 비활성화/모드 변경/퇴장 때 소스와 예약을 정리한다.
탭 복귀 후에는 플레이/오디오 활성화 버튼으로 정지된 Context를 재개한다.

Esc 메뉴에 전체 음량·음소거·오디오 재활성화가 있다. 설정은 localStorage에 보관하고
접근 실패 시 기본값을 쓴다. mute 상태에서는 새 재생 소스를 만들지 않는다.
카메라 기준 좌우 pan·거리 감쇠, 출력 headroom·compressor와 ±2% 피치 변화를 쓴다.
이는 초기 믹싱 설정이며 실제 음장·장비 측정값이 아니다.

설정/구현 위치:
- `apps/web/game/audioConfig.ts`: 음원 매핑, 음량, 거리, 최소 재생 간격, 버퍼 상한.

`public/assets/audio/net.wav` (designerschoice / Nicholas Judy, CC BY 4.0)를 사용한다.
원본을 변경 없이 복사한다. 기존 백보드 충돌 사건과 서버 확정 득점 사건에 연결하며,
패스는 네트음을 발생시키지 않는다. 클린/접촉 후 득점에 같은 네트 녹음을 사용한다.
Esc 오디오 메뉴에서 네트 제작자·라이선스와 전체 출처 문서를 확인할 수 있다.

이 두 원본·정적 복사본은 Git에서 제외하지 않으므로 함께 커밋하면 GitHub → Vercel
배포에 포함된다. Mixkit 드리블/바운드의 기존 제외 정책은 별개로 유지한다.
음원 준비 스크립트는 Mixkit 원본이 없으면 기존 배포 자산을 보존하며 계속 실행한다.
이제 실제 녹음은 드리블·바운드·백보드·네트 4종이고 합성 임시음은 나머지 6종이다.

이번 연결에서는 원본과 배포 파일 바이트 일치 및 WAV 형식을 확인했다.
테스트·타입 검사·빌드와 실제 청취는 실행하지 않았다. 새로고침 후 플레이를 눌러
백보드에 맞는 슛에서 새 타격음, 득점에서 새 네트음이 나는지 확인한다.
패스·실패 슛에서는 네트음이 없어야 하며, Esc 메뉴에서 출처 링크도 확인한다.

### 바운드 음원 5종 무작위 재생

`sounds/bounce_01.WAV` ~ `bounce_05.WAV`를 정적 자산의 같은 소문자 파일명으로
복사했다. 드리블·크로스오버 바닥 접촉 및 자유 공 바닥 충돌에서 매번 5개 중 하나를
무작위로 선택한다. 같은 소리가 연속 선택될 수 있다. 한 파일은 한 번만 디코딩하고
두 효과가 버퍼를 공유한다. 일부 파일 로딩에 실패하면 로딩된 파일 중에서 선택한다.
기존 접촉 판정·작은 바운드 억제·재생 간격·음량·동시 재생 상한은 유지한다.
Mixkit 단일 드리블/바운드 파일은 이제 선택하지 않는다.

이번 변경은 원본과 정적 자산 파일 일치를 확인했으며 테스트·타입 검사·빌드·청취는
실행하지 않았다. 새로고침 후 플레이하여 정지 드리블/Q 크로스오버/슛 후 바닥 바운드에서
소리가 번갈아 나오는지 확인한다. 음소거와 백보드·네트 소리도 기존처럼 유지되어야 한다.

### 걷기·달리기 발자국 소리 제거

내 캐릭터와 상대 모두 걷기·달리기 발자국 효과음을 제거했다. 재생 사건 생성,
음원 로딩 설정, 합성 생성 경로와 step.wav 정적 자산을 제거했다.
이동 모션과 다른 효과음은 유지한다. 테스트·타입 검사·빌드·청취는 실행하지 않았다.
새로고침 후 걷기/Shift 달리기에서 발자국 소리가 없고 드리블 소리는 유지되는지 확인한다.

### 득점 시 네트 모션

`apps/web/game/createNet.ts`에서 림에 고정된 네트 위쪽은 유지하고, 득점 시 아래쪽을
빠르게 당겼다가 작은 흔들림과 함께 약 0.95초에 걸쳐 복원한다. NET_MOTION의 pull,
flare, sway, attack, duration으로 강도·속도를 조정한다. 기존 Mesh를 갱신하며 물리·득점
판정에는 관여하지 않는다. 온라인은 기존 서버 확정 net 사건과 공의 보간 표시 시각을
사용하고, 사건 ID로 중복을 막으며 과거 사건은 건너뛴다. 음소거 상태에서도 움직인다.
오프라인 R/시나리오 변경 시 모션과 예약을 초기화한다.
테스트·타입 검사·빌드·브라우저 검증은 실행하지 않았다. 새로고침 후 득점에서 네트가
당겨졌다가 복원되는지, 실패/패스에는 반응하지 않는지, 음소거에서도 움직이는지 확인한다.

### 공격자 1인칭 표시·수비 판정 여유 조정

내가 공을 소유하거나 슛/패스 릴리스 동작 중이면 1인칭 몸통·골반·다리만 숨기고
팔·손·공은 유지한다. 공을 잃고 릴리스 동작이 끝나면 수비 시 몸 표시로 돌아간다.
다른 플레이어와 더미는 계속 전신으로 보이며, 몸통을 조준 pitch로 꺾지 않는 수정도 유지한다.

`packages/game-core/src/court.ts`의 초기 튜닝값을 다음처럼 변경했다.
- BODY.radius: 0.30 → 0.42m (몸 충돌 지름 0.60 → 0.84m). 원형 실린더이므로
  좌우뿐 아니라 모든 수평 방향에 적용된다. 서버·클라이언트·고정 더미가 같은 값을 사용한다.
- 블록 반경: 0.22 → 0.38m, 손 목표 높이: 발 기준 1.90 → 2.00m,
  전방 위치: 0.36 → 0.40m. 공 반지름을 포함한 기존 swept 판정을 유지한다.
- 블록 active: 0.36 → 0.54초, 회수: 0.30 → 0.24초. 준비 0.06초와
  재사용 대기 0.85초는 유지한다. 판정이 점프 정점을 포함하도록 기간을 늘렸다.
- 블록 중 어깨를 최대 0.09m 올렸다가 복원해 높아진 손 목표와 팔 모션을 맞춘다.
  점프 높이·중력·슛/패스 속도는 변경하지 않는다.

테스트·타입 검사·빌드·브라우저 검증은 실행하지 않았다. 두 창을 최신 코드로 갱신하고
게임 서버도 갱신한 뒤 공 소유/릴리스 중 몸 숨김, 상대 전신 표시, 정면 몸 충돌,
양쪽 이동·점프 접촉, 점프슛에 대한 타이밍별 블록을 확인한다.
F3로 넓어진 몸 실린더와 블록 영역을 볼 수 있다. 실제 수비 난이도는 플레이 후 튜닝한다.

### 림 5종·swish 7종 무작위 재생

`sounds/rim/rim_01.WAV` ~ `rim_05.WAV`는 실제 림 충돌 때, `sounds/swish/swish_01.WAV`
~ `swish_07.WAV`는 서버 확정 득점 때 기존 AudioManager가 무작위 선택한다.
같은 음원이 연속 선택될 수 있다. 클린/접촉 후 득점에 같은 swish 목록을 사용한다.
드리블 원본을 옮긴 `sounds/bounce/` 경로도 음원 준비 스크립트에 반영했다.
각 파일은 한 번 디코딩해 재사용하고 기존 중복 억제·거리 감쇠·음량을 유지한다.
이전 단일 네트음의 제작자를 새 swish 음원의 제작자로 표시하지 않도록 크레딧도 정리했다.
테스트·타입 검사·빌드·청취는 실행하지 않았다. 새로고침 후 여러 번 림을 맞히고 득점해
무작위 변화를 확인한다. 패스/실패에는 swish가 없어야 하며, 드리블·백보드는 기존처럼 유지된다.

### 충전 중 슛↔패스 전환·오른팔 팔로스루

좌클 슛 충전 중 우클 down이면 패스, 우클 패스 충전 중 좌클 down이면 슛으로 전환한다.
충전량은 새 동작에서 0부터 시작하며 현재 공 위치에서 Gather로 이어져 순간이동하지 않는다.
동시에 두 충전을 유지하지 않는다. 이전 버튼의 뒤늦은 mouseup은 발사를 만들지 않으며,
선택된 버튼을 놓을 때만 발사한다. 이미 release를 예약한 뒤에는 전환하지 않는다.
온라인 서버도 이전 공격 버튼을 해제하고 새 충전 시작 시각을 저장한다. Esc/blur/
소유권 상실/초기화의 취소 정책은 유지한다.

슛 릴리스 후 오른손을 약 0.08초에 걸쳐 위로 뻗고, 팔로스루를 유지한 뒤 부드럽게 내린다.
오른손 손목을 꺾으며 왼손은 먼저 내린다. SHOT_FORM.followHoldSeconds(0.28초)와
followReturnSeconds(0.24초), followReachSeconds, followHandUp/Forward로 조정한다.
슛 전용 총 0.52초 동안 RELEASE 표시 상태를 유지하며 패스의 기존 0.18초 복귀는 유지한다.
공 비행·점수 판정은 팔로스루와 독립적으로 계속 진행한다.

테스트·타입 검사·빌드·브라우저 검증은 실행하지 않았다. 두 클라이언트와 서버를 갱신한 뒤
좌→우/우→좌 전환, 이전 버튼 먼저 놓기, 새 버튼의 짧은 클릭, Esc 취소를 확인한다.
슛 후 내 화면과 상대 화면에서 오른팔이 잠시 뻗고 왼손은 먼저 내려오는지 확인한다.
