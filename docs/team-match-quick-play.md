# 정식 2대2 경기와 빠른 플레이

## 기존 모드 보존과 변경 범위

- `duel`: 기존 2인 정식 1대1, 기존 준비/점수/재경기 정책 유지.
- `practice`: 기존 2인 자유 연습, 즉시 플레이.
- `practice2v2`: 기존 4인 연습, 팀 표시만 적용하며 정식 승패 없음.
- **`teamDuel`**: 정식 반코트 2대2. 최대 4명, A/B 각 2명. 생성 시 서버에서 모드 확정.

`OnlineWorld`의 한 월드/한 공, 기존 이동 예측·ACK·원격 보간·4인 충돌·공 물리·패스·닉네임·채팅을 재사용한다.
새 시뮬레이션이나 모델, 패키지, 로그인/DB/Redis를 추가하지 않는다. npm/package-lock 유지.
사용자의 이전 미커밋 2대2 연습 변경에 이어 구현했으며 이전 작업을 되돌리지 않았다.

주요 변경 파일:
- game-core: `match.ts`, `online.ts`, `teamMatch.test.ts`
- protocol: `rooms.ts`, `quickPlay.ts`
- game-server: `server.ts`, `publicRooms.ts`, `quickPlay.ts`, `teamMatch.test.ts`, `quickPlay.test.ts`
- web: `TeamMatchPanel.tsx`, `TeamPanel.tsx`, `OnlineMenu.tsx`, `Game.tsx`, `ScoreBurst.tsx`,
  `game/quickPlay.ts`, `onlineClient.ts`, `createGame.ts`, `remoteCharacters.ts`, `roomDirectory.ts`, `menuState.ts`
- 브라우저 재현: `scripts/probe-team-match-browser.mjs`

## 확정 규칙과 상태

팀 합산 11점 이상이면 즉시 승리한다. 2점 차 승리 조건 없이 기존 정식 경기의 2점/3점 구역을 재사용한다.
첫 공격 팀은 서버 난수로 A/B를 선택하며, 해당 팀 slot 정렬 명단의 다음 담당자에게 공을 준다.
공격 시작 담당자는 팀별 원형 인덱스로 교대한다. 득점 후에는 실점 팀의 다음 담당자가 공격한다.
다음 공격은 기존 1초 준비 시간과 안전 재배치를 사용하고 목표 점수 도달 시 교대 없이 종료한다.
공격자 (0,-1.5), 동료 (-1.7,-1.5), 수비자 (0,0.2)/(1.7,0.2) XZ m이며 실린더 간격을 확보한다.

| 상태 | 정책 |
| --- | --- |
| WAITING | 총 4명·각 팀 2명·전원 준비 필요. 팀 변경 가능 |
| COUNTDOWN | 기존 3초 카운트다운. 팀 변경/새 참가 금지. 준비 취소나 퇴장 시 WAITING |
| PLAYING | 이동/행동 허용. 팀 변경·새 참가·빈자리 채우기 금지 |
| FINISHED | 승리 팀/최종 팀 점수/개인 득점 보존. 네 명 전원 재경기 동의 필요 |
| ABORTED | 실제 참가자 연결 종료로 중단. 정상 승리와 구분하며 신규 참가 금지 |

팀 변경 성공과 참가/퇴장으로 구성원이 바뀌면 전체 준비를 해제하고 이유를 표시한다.
COUNTDOWN은 네 명의 실제 참가자 모두가 준비해야 시작하므로 미소비 예약만으로 시작하지 않는다.
공식 경기 Room은 WAITING 외 상태에서 Colyseus lock(), 대기 복귀 시 unlock()을 직렬 적용한다.
최종 입장 검증은 항상 world.canJoin()/팀 정원으로 다시 수행한다. blur는 퇴장이 아니다.

재경기는 네 명 전원 동의 시 경기 id/epoch를 증가시켜 한 번만 시작한다. 팀은 유지하고 첫 공격 팀은 교대한다.
점수·개인 기록·공·행동·예약 발사·클리어 상태는 초기화한다. FINISHED에서 퇴장해도 결과는 바꾸지 않고 재경기는 막는다.
상태 전환은 기존 입력 큐 retire, epoch 검증과 relocationEpoch를 재사용하며 seq/ACK를 초기화하지 않는다.

## 공격권·득점·수비

- 팀 기준 공격권: 상대 팀이 실제 공을 획득하면 클리어 필요. 자유 공/블록 접촉만으로는 바꾸지 않는다.
- 같은 팀 패스·캐치·공격 리바운드는 클리어 상태를 유지한다.
- 공 소유자의 수평 림 거리 >= 기존 CFG.arc(6.75m)일 때 클리어 완료. 기존 외곽 선과 같은 기준이다.
- 클리어 전 서버에서 슛 down/up와 예약된 슛 발사를 차단한다. 이동과 패스는 허용한다.
- 릴리스 시 matchId/shotId/shooterId/shooterTeamId/득점 자격/구역 점수를 고정 기록한다.
- 같은 슛은 한 번만 팀 점수와 개인 점수에 반영한다. 현재 소유자/팀으로 과거 슛을 재귀속하지 않는다.
- 블록 후 기존 슛 자격은 유지한다. 결과 확정 이후 득점/입력으로 결과를 바꾸지 않는다.
- 정식 2대2만 아군 스틸과 아군의 슛/패스 블록을 막는다. 기존 연습 정책은 그대로다.
- 패스는 기존 시야·충전 방식이며 상대 가로채기도 유지한다. 동시 캐치/스틸/블록 후보는 기존 slot 기반
  순환 시작점으로 검사해 유효한 첫 후보 한 명만 획득한다. 정밀한 거리 동률 비교나 확률 판정은 추가하지 않는다.
- 아군/적군 모두 기존 실린더와 점프 중 수평 충돌을 유지한다. 파울/자유투/새 공격 제한시간은 없다.
- 정식 2대2 아웃 시 마지막 터치의 반대 팀에서 기존 순환 후보를 선택한다. 연습/1대1 정책은 유지한다.

## 빠른 플레이: 선택·예약·생성·취소

온라인 플레이에서 2대2 경기 → 빠른 플레이. 기존 방 찾기/만들기/코드 참가도 유지한다.
같은 게임 서버의 공개 `teamDuel` WAITING 방만 대상으로, 실제 Room 상태·잠금·예약 포함 정원을 확인한다.
후보를 무작위 선택하고, 없으면 서버 기본 이름의 공개 정식 방을 생성한다. 비공개/연습/진행/결과/중단 방은 제외한다.

`POST /quick-play`는 requestId/검증된 닉네임/색상만 받는다. 사용자 모드·정원·팀·메타데이터는 허용하지 않는다.
클라이언트는 기존 WSS/WS 환경 변수에서 HTTPS/HTTP 주소를 유도하며 별도 주소를 하드코딩하지 않는다.
기존 정확한 허용 origin 목록을 사용한다. Colyseus의 기존 OPTIONS 처리/CORS 범위는 확대하지 않는다.

서버 배정 구간만 Promise 큐로 짧게 직렬화한다. 접속 완료나 게임 틱은 잠그지 않는다.
`matchMaker.query/createRoom/reserveSeatFor`와 SDK `consumeSeatReservation`을 사용한다.
예약도 Colyseus 정원에 포함되므로 동시 네 요청은 한 방, 다섯 번째는 다음 방으로 배정된다.
삭제/만석/상태 전환이 확인되는 경쟁만 최대 3회 다시 조회한다. 건강한 후보의 통신/서버 오류는 503으로 반환하며
오류를 새 방 생성으로 숨기지 않는다. 모든 성공/실패에서 배정 큐가 해제된다.

설정(`protocol/quickPlay.ts`): payload 최대 1200 bytes, 전체 서버 분당 120회, 배정 대기 최대 32개,
대기 시작 전 8초 초과 요청은 실행하지 않음, 중복 기록 최대 256개·완료 후 60초 보관.
진행 중 요청은 TTL 청소로 지우지 않는다. 같은 requestId는 같은 Promise/예약을 반환하고 다른 본문은 409로 거절한다.
예약이 만료된 requestId를 재사용해 다른 방을 만들지 않는다. 재시도 클릭은 새 ID를 쓴다.
이 제한은 단일 프로세스 MVP의 전체 제한이며 사용자 인증 기반 제한이 아니다.

연결 취소는 기존 ConnectionAttempt 세대를 사용한다. 늦게 반환된 예약은 공개 SDK로 연결을 소비한 뒤 즉시 leave하여
좌석을 정리하고 경기 화면으로 진입하지 않는다. 결과 화면에서 재검색 중에도 이전 작업이 새 탐색을 덮어쓰지 않는다.
응답 자체가 유실되거나 네트워크 장애로 소비할 수 없는 예약은 Colyseus 기본 15초 만료로 반환된다.
0.17의 비공개 예약 자료구조를 직접 수정하지 않으며 이 경우 즉시 좌석 반환을 보장하지 않는다.

참고한 공식 문서와 설치 구현:
- https://docs.colyseus.io/matchmaker
- https://docs.colyseus.io/migrating/0.17 (평탄한 roomId/processId/sessionId 예약 형식)
- https://0-17.docs.colyseus.io/room
- 설치된 core 0.17.56 / SDK 0.17.43의 MatchMaker/Room/Client 타입과 구현 확인

## 실행·검증

Windows:
```powershell
npm.cmd run dev:online
```
서로 다른 브라우저/프로필 네 개에서 온라인 플레이 → 2대2 경기 → 빠른 플레이를 누른다.
또는 방 만들기 → 정식 2대2로 만든 뒤 같은 Room ID로 참가한다. 네 명 모두 준비하면 카운트다운 후 입장할 수 있다.
서버 권위 변경이므로 웹과 게임 서버를 함께 갱신해야 한다. 외부 배포는 수행하지 않았다.

실행한 자동 검사:
- 단계 A: 관련 37개 회귀/경기 테스트 통과 후 실제 4 SDK 클라이언트와 핵심 규칙 7개 통과. 그 뒤 B 진행.
- `npm.cmd test`: 254개 통과.
- `npm.cmd run test:server`: 16개 통과.
- `npm.cmd run typecheck`: 웹/서버 통과.
- `npm.cmd run build`: 웹 정적 프로덕션 빌드 및 서버 번들 통과.
- 빠른 플레이의 큐/요청 수명 보완 후 관련 서버 테스트 3개와 타입 검사를 별도로 재확인.

브라우저 확인은 `node --import tsx scripts/probe-team-match-browser.mjs`로 핵심 흐름 한 번만 실행했다.
esbuild로 묶은 실제 Game 소스 + 실제 로컬 서버에서 Chrome 두 창과 SDK 두 개(총 4접속)를 사용했다.
빠른 플레이 같은 방 참가, 각 브라우저에서 원격 캐릭터/라벨 3개, 전원 준비/PLAYING,
실제 퇴장으로 ABORTED, 결과 화면에서 새 빠른 플레이와 목록 복귀를 확인했다. 브라우저 예외/스크린샷/녹화 0.

미검증: 실제 사람이 네 브라우저를 조작하는 경기, 브라우저에서 11점 종료/재경기/연속 슛·패스,
Next 배포 환경의 플레이, 장시간 예약 부하와 성능 수치. 11점/재경기/득점과 공 규칙은 자동 테스트 범위다.
단일 서버용이며 다중 서버 매칭, 재접속 복원, 경기 중 충원, 랭크·파티 매칭은 구현하지 않았다.
